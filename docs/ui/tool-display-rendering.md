# Renderização de Exibição de Tool

> **Estado atual**: a row da V4 reutiliza o renderer unificado de `ToolCall` por meio da camada de adaptação; este documento descreve a fronteira de renderização atual.

## Objetivo

Unificar o ponto de entrada de exibição de tools na área de chat, evitando acumular ramificações por `kind` dentro da conversation row, e ao mesmo tempo deixar uma porta de extensão para a renderização dedicada de tools futuras como `execute`, `search` e `fetch`.

## Estrutura atual

- `packages/ui/src/lib/toolDisplay.ts`
  - Responsável por normalizar `ChatToolCall` em `ToolDisplayModel`
  - Emite `inlinePreview`, `viewerSource`, `showInput`, `showOutput`, `showKind`
- `packages/ui/src/lib/codeViewer.ts`
  - Responsável por extrair os dados de pré-visualização de `text / patch / file / image`
  - Não decide diretamente a UI final, apenas fornece a capacidade de pré-visualização
- `packages/ui/src/v4/ConversationRowView.tsx` e `packages/ui/src/v4/toolCallRowAdapter.ts`
  - Adaptam o `ToolCallRow` da V4 na entrada exigida pelo renderer unificado, sem duplicar dentro do componente de row as UIs de cada tipo de tool
- `packages/ui/src/ToolCallBlocks.tsx`
  - Responsável pelo registro e seleção do renderer; `packages/ui/src/ToolCallBlocks/renderers/` hospeda as exibições dedicadas por kind/family
- `packages/ui/src/ToolCallBlocks/ToolCallBody.tsx`
  - Responsável pela pre-visualização genérica de parâmetros, resultado, arquivos e Markdown

## Visibilidade no fluxo da sessão

- `EnterPlanMode` é uma fronteira interna de troca de modo da sessão e não oferece ao usuário detalhes acionáveis; o fluxo principal da sessão não renderiza sua tool row em `inputStreaming` / `running` / estado terminal.
- O filtro de visibilidade atua apenas sobre a unidade de renderização da UI: a projeção do protocolo ainda preserva o `ToolCallRow` original, e estados de execução, recuperação a frio, troca de modo e rastros de diagnóstico não podem ser perdidos por causa da exibição oculta.
- O filtro é executado sobre a unidade de renderização compartilhada entre o desktop `desktop-continuous` e o celular `web-remote-replayable`, sem reescrever os snapshots, a recuperação de gaps ou a ordem de mensagens dos dois tipos de delivery.
- Os conversation work items derivam execuções Shell consecutivas não somente-leitura em um agrupamento de UI `Execute`; esse nó pai não é uma chamada de ferramenta de protocolo e, ao ser expandido, continua reutilizando o `ExecuteToolCallBlock` individual. O PermissionDialog não passa por esse caminho de agregação e continua sendo aprovado e exibido individualmente, conforme a tool call real.

## Formas de extensão

- Ao adicionar otimizações dedicadas a um novo kind, prefira acrescentar uma strategy em `toolDisplay.ts`
- A strategy deve fazer apenas "aprimoramento da decisão de exibição", sem reescrever o esqueleto principal de renderização
- Tools do tipo arquivo devem preferentially reutilizar o resultado de extração de pré-visualização de `codeViewer.ts`
- Para recursos multimídia, se forem imagens, prefira o preview do tipo `image`; outros binários continuam seguindo o aviso de fallback

## Renderers de Tool Dedicados

- O layout expandido das ferramentas `Node REPL` / Browser Use permanece transparente e mantém a mesma linha de base horizontal do corpo do resumo da ferramenta; não é permitido adicionar novamente padding horizontal em bloco inteiro além do espaçamento de detalhe de `ToolLayout`. O bloco de conteúdo de resultado textual e o código/pilha de erro expandidos por "ver detalhes da execução" usam `bg-card border border-border rounded-xl`; imagens, o botão "ver detalhes da execução" e o próprio layout colapsado permanecem fora do cartão. Resultados curtos de linha única, não-JSON e com no máximo 160 caracteres são exibidos como corpo secundário comum; JSON, multilinha ou logs mais longos continuam usando CodeBlock com ações de copiar/quebra de linha. Resultados de imagem na área expandida da mensagem sempre usam coluna única, evitando que pontos de quebra responsivos cortem miniaturas em colunas duplas estreitas em barras estreitas do desktop e na Web móvel; o comportamento do visualizador de imagens grandes permanece inalterado.
- A área expandida da ferramenta `CUA` exibe apenas ação, resultado, motivo da falha, sugestão, captura de tela, permissão, ambiente, lista e estado da aplicação voltados ao usuário, sem oferecer entrada de "ver dados brutos" para o JSON completo da tool call. O input, output, display e metadados de ciclo de vida originais da chamada de ferramenta continuam sendo mantidos conforme o protocolo e a cadeia de persistência existentes, apenas não entram na interface expandida de CUA compartilhada entre desktop e Web móvel; a capacidade de dados brutos dos outros renderers de tool não é afetada.
- `ReadSessionContext` é renderizado por `ReadSessionContextToolCallBlock` e não passa pelos blocos JSON de fallback `Parameters` / `Result`.
- A linha de resumo exibe o `query` desta leitura de contexto e usa `sessionId` como identificador secundário.
- A área expandida exibe apenas `query` e o conteúdo de contexto retornado; se o output for um objeto estruturado, lê-se preferencialmente `output.content`, com fallback para output textual ou `rawOutput`.
- `SendMessage` pertence à family `message` e é renderizado por `SendMessageToolCallBlock`. No estado recolhido, forma uma frase completa com "enviado/enviando + input `summary` + de/para + agent de destino `to`"; no estado expandido, exibe apenas o agente de destino, o resumo e o corpo da mensagem, sem exibir status de entrega, ids de message/agent/task, caminho de saída, result ou o JSON completo da tool call. Quando destino, resumo e mensagem ainda não tiverem chegado, a expansão deve ser desabilitada; é proibido exibir um painel de detalhe vazio sobre input em streaming ou snapshot com campos ainda não carregados.
- Os dados principais de exibição de `SendMessage` usam o display payload `local_agent_message` gerado pelo Core, além da formatação de model content e da concatenação do hook additional context. O payload mantém apenas `status`, `error` de falha e `message` de resultado, e não deve carregar nem exibir entrega, ids de message/agent/task ou caminho de saída; `error` e `message` devem estar cada um sujeito a um orçamento de 4 KiB em UTF-8, preservando o code point completo e acrescentando o marcador `...[truncated]` ao exceder, para evitar que o display amplie eventos ao vivo e snapshots persistidos contornando o tool result budget. O `send_message` em minúsculas tem outra semântica, a session mailbox, e não pode reutilizar a identidade, o display ou o renderer de `SendMessage`.
- Se o display de `SendMessage` retornar `status: "failed"`, mesmo que a tool call externa já esteja completed, deve-se exibir "falha no envio da mensagem" e o status de falha de negócio; uma falha real da tool também não pode continuar exibindo "enviado". Saída estruturada, string JSON, model content em texto puro e `rawOutput` / `result.content` servem apenas como fallbacks de compatibilidade para snapshots antigos/provedores; é proibido inferir sucesso ou falha a partir de mensagens de erro.
- O estado recolhido de `SendMessage` deve cobrir explicitamente todos os estados terminais: `completed` exibe "enviado", `failed` ou falha de negócio do display exibe "falha no envio da mensagem", `denied` exibe "envio negado" e `stopped` exibe "envio interrompido"; estados terminais não bem-sucedidos não podem cair em texto de sucesso.
- `TaskStop` pertence à family `task-control` e é renderizado por `TaskStopToolCallBlock`. O estado recolhido usa apenas o texto de ação parando/parado e o `task_id` (na fase de entrada, com compatibilidade para o `shell_id` obsoleto), e não pode exibir `task_type`; no estado expandido, a linha de resumo continua preservando o task id, e a área de detalhes exibe apenas task type, descrição do tarefa ou comando, e a mensagem de resultado, sem repetir o task id nem exibir o JSON completo da tool call.
- Os dados principais de exibição de `TaskStop` usam o display payload `task_stop` gerado pelo Core, cujos campos contêm somente `taskId`, `taskType`, `command` opcional, `message` de resultado e `truncated` opcional. `command` e `message` devem estar cada um sujeito a um orçamento de 16 KiB em UTF-8, e qualquer campo truncado define `truncated: true`, evitando que o display amplie eventos ao vivo, snapshots persistidos e DOM expandido contornando o tool result budget; o estado expandido da UI deve sinalizar explicitamente que os detalhes foram truncados. Eventos ao vivo são lidos de `raw.result.display`, a recuperação persistida de `raw.display`, e outros provedores podem ler de `raw.rawOutput.display`; as três entradas devem passar pelo mesmo UI reader com validação estrita de kind/campo.
- O output/model content de sucesso de `TaskStop` continua mantendo o contrato original da ferramenta; o runtime deve fazer com que o `command` de `local_bash` represente o comando real e o `command` de `local_agent` represente uma `description` curta, sem colocar o `prompt` completo do subagent no resultado. Para `local_agent`, a UI exibe o `command` do display `task_stop` confiável como "descrição da tarefa" com estilo de corpo de texto; tarefas de tipo comando continuam sendo exibidas como "comando" com estilo monoespaçado. Resultados históricos de `local_agent` sem display não podem exibir o antigo `output.command` como descrição, pois esse campo pode guardar o prompt completo; o campo antigo só pode ser usado para reconhecer com precisão e compactar o texto padrão de sucesso. A projeção de display só é responsável por remover da mensagem padrão de sucesso o conteúdo já exibido separadamente pelo campo `command`: `Successfully stopped task: <taskId> (<command>)` aparece em "Resultado" na UI como `Successfully stopped task: <taskId>`. Para resultados históricos sem display, a UI faz apenas a correspondência exata desse mesmo template, e qualquer texto de resultado personalizado deve ser preservado como está.
- `TaskStop` continua compatível com objetos estruturados antigos, strings JSON e `rawOutput`. Se um resultado histórico tiver hook additional context, só é permitido reconhecer o envelope explícito `\n\n[Hook additional context]` e fazer o parse do JSON da primeira parte; não é permitido truncamento por prefixo arbitrário nem adivinhação de texto. A operação de parada em si não usa cor destrutiva; apenas estados reais de falha continuam reutilizando o status de falha e o tooltip de erro de `ToolLayout`.
- O estado recolhido de `TaskStop` deve cobrir explicitamente todos os estados terminais: `completed` exibe "parado", `failed` exibe "falha ao parar a tarefa", `denied` exibe "operação de parada negada" e `stopped` exibe "operação de parada cancelada"; falha, negação ou interrupção não podem coexistir com "parado".
- Se `failed` / `denied` / `stopped` de `TaskStop` tiverem um motivo de erro, o estado expandido exibe esse motivo como "Resultado"; se não existirem task type, descrição da tarefa ou comando, resultado e aviso de truncamento, a expansão deve ser desabilitada, sendo proibido um painel de detalhes clicável porém vazio.
- `TaskOutput` pertence à family `task-control` e é renderizado por `TaskOutputToolCallBlock`. O estado recolhido usa `task_id` monoespaçado como conteúdo principal, e o status é projetado pela prioridade "estado terminal da execução da tool > status da recuperação > status da task consultada": falha na execução da tool exibe "execução falhou", em execução exibe "tarefa em execução", espera esgotada exibe "tempo de espera esgotado", leitura bem-sucedida de task completed exibe "obtido", failed/lost exibe "tarefa falhou" e cancelled/killed/stopped exibe "tarefa parada". Status de task desconhecido é exibido como é; é proibido tratar toda leitura bem-sucedida como task bem-sucedida.
- Os dados principais de exibição de `TaskOutput` usam o display payload `task_output` gerado pelo Core, contendo apenas `retrievalStatus`, `taskStatus` opcional de no máximo 64 caracteres, `output` opcional de no máximo 2000 caracteres e `truncated` opcional. O `task_id` continua sendo lido direto do input da tool, sem duplicação no display. O output usa `trimEnd()` e mantém os primeiros 2000 caracteres; output em branco não gera campo, e output parcial já obtido durante a execução pode ser exibido. Somente output não vazio oferece entrada de expansão, e a área expandida usa um `<pre>` com rolagem e altura máxima fixa; ao truncar, avisa que o conteúdo subsequente foi omitido. Task type, description, error, prompt, result, output path e o XML/JSON original do provedor não podem entrar no display, no corpo do resumo ou no conteúdo expandido; falha real de execução da tool continua reutilizando o tooltip de status de falha genérico de `ToolLayout`, exibindo o motivo do erro via `context.errorText` no hover/copy, sem gerar por isso uma área expandida.
- `RespondToCoordinator` pertence à family `message` e é renderizado por `RespondToCoordinatorToolCallBlock`. O estado recolhido usa apenas o input `summary` como conteúdo principal e não oferece área expandida; em execução exibe "respondendo", em sucesso exibe "resposta enfileirada", e falha de negócio ou de execução exibe "execução falhou", com negação e parada exibindo os respectivos estados terminais. "Enfileirada" significa apenas que o response command entrou na fila de comandos do runtime pai, e não pode ser escrito como entregue, lido ou processado.
- Os dados principais de exibição de `RespondToCoordinator` usam o display payload `respond_to_coordinator` gerado pelo Core, contendo apenas `status: "success" | "failed"`. `message`, `responseId`, `error` e o result original não podem ser copiados para o display, o corpo do resumo ou o conteúdo expandido; falha real de execução da tool continua reutilizando o tooltip de status de falha genérico de `ToolLayout`, exibindo o motivo do erro via `context.errorText` no hover/copy, e `status: "failed"` de negócio não gera detalhes de erro do nada. Uma tool row child comum só é materializada no tópico da sessão child; a sessão pai continua exibindo apenas o resumo de Agent/Task, e não é preciso restaurar mirrored child tool row por causa de um card exclusivo.
- Novos displays são transportados por completed tool metadata e por `ToolCallRow.display` da V4. Quando registros antigos não têm display correspondente, os dois renderers usam apenas o input e o ciclo de vida genérico da tool para exibir um resumo mínimo, sem fazer parse do XML/JSON visível ao provedor e sem nova migração de persistência.
- O WDIO desktop oficial reutiliza a verificação do ciclo de vida do Agent em background para validar as duas cadeias de projeção: o caso de sucesso chama de verdade `TaskOutput` na sessão pai e expande o output, depois entra na sessão child a partir do resumo do Agent para verificar o summary/"resposta enfileirada" de `RespondToCoordinator` e o isolamento da sessão pai; o caso combinado de erro faz o TaskOutput consultar uma task inexistente e faz o child chamar um RespondToCoordinator sem o `message` obrigatório, cobrindo atualmente o estado terminal de erro das duas tool rows, o texto unificado "execução falhou", a ausência de provider error wrapper ou erro bruto no corpo do card e a fronteira child-only. As asserções WDIO que exibem o `context.errorText` correspondente ao passar o mouse sobre os dois cards de erro ainda não foram adicionadas, portanto O19 permanece `partial`. O E2E não reenumera os estados de recuperação/task, a falha de negócio da fila, a fronteira de 2.000 caracteres nem o mobile replayable; essas combinações são cobertas por testes direcionados do Core display, da projeção/wire da V4 e do renderer compartilhado.
- Todos esses renderers reutilizam `ToolLayout`, `ToolSnapshotFieldNotice`, semantic color tokens, a tipografia de corpo `text-ui-base` e ícones lucide. O command no summary recolhido das ferramentas Execute/Shell usa fonte UI sans, consistente com a mesma linha de resumo; o corpo do comando expandido continua usando fonte monoespaçada. As props JSX passadas ao `ToolLayout` memoizado devem manter referência estável via `useMemo`; o layout de detalhes deve quebrar linha verticalmente de forma natural em telas estreitas e ser compatível com desktop/Web, Zai Light/Zai Dark e com comprimentos de texto em chinês e inglês.
- Os resumos de `Read` / `Edit` / `Write` priorizam preservar o nome do arquivo quando o fluxo da sessão fica estreito: em um conversation container mais estreito que `360px`, oculta-se primeiro o rótulo de ação, o badge de origem e o caminho do diretório pai; o chip de arquivo usa a largura restante e trunca internamente; ícone de arquivo, estatísticas de diff e entrada de expansão continuam visíveis. Em largura normal ainda exibe o rótulo de ação e o caminho completos, e a divisão do desktop e a Web móvel compartilham a mesma regra de container.
- Todos os ToolCall mantêm o ícone estático de kind durante a execução, sem substituí-lo por ícone de loading giratório; o estado em execução é expresso pelo texto de kind em varredura, pelo texto de status e pelo conteúdo do resumo, evitando o custo contínuo de renderização de animação quando muitos toolcalls estão em streaming simultaneamente.
- O texto dos ToolCall segue uniformemente "nome de ação no estado em execução, nome de categoria estável no estado terminal": em chinês, o kind label de `pending` / `in_progress` usa `正在 + ação`; em inglês mantém as palavras de ação existentes, concisas e naturais (como `Reading`, `Sending`, `Working`), sem reescrita mecânica para simetria de frase. Ao entrar em `completed` / `failed` / `denied` / `stopped`, volta-se ao nome de categoria sem o prefixo "已"; objetivo, comando, arquivo e resultado de negócio continuam no corpo do resumo, e estados anormais como falha, negação e parada continuam expressos pelo status label. Por exemplo, um único Read exibe `正在读取 · package.json` e, ao concluir, `读取 · package.json`; um único Execute exibe `正在执行 · pnpm test` e, ao concluir, `终端 · pnpm test`. É proibido usar ações de sucesso como "已读取"/"已执行" como nome de categoria terminal, e é proibido repetir a mesma ação em progresso no nome da categoria e no corpo do resumo.
- Status de negócio dedicado tem prioridade sobre o texto genérico de ciclo de vida: o resultado de sucesso de `RespondToCoordinator` continua sendo "resposta enfileirada", `TaskOutput` continua distinguindo tarefa em execução, tempo de espera esgotado, tarefa falhou e tarefa parada, e `TaskStop` continua distinguindo parada bem-sucedida da tarefa de negação/cancelamento da própria operação de parada. O nome da categoria só explica o que a tool é e não pode sobrescrever esses resultados de negócio.
- Explore, Terminal e Changes só criam um grupo pai sintético de UI quando, dentro do mesmo segmento de trabalho visível, há 2 ou mais tools do mesmo tipo em sequência; quando o maior segmento consecutivo tem apenas 1 tool, a tool original é exibida diretamente, sem grupo pai. Na fase de streaming, a primeira tool já aparece imediatamente como a tool original, e o grupo pai com identidade ancorada na primeira tool só é criado quando a segunda tool do mesmo tipo chega. Tools de tipos diferentes, reasoning visível e texto do assistant continuam cortando o segmento; reasoning oculto e Shell aguardando a classificação do comando continuam tratados como fronteiras transparentes.
- As ferramentas Explore agregadas comuns (busca, listagem de diretório, leitura de arquivo etc.) permitem que o usuário expanda/recolha manualmente mesmo no estado em execução; o estado em execução indica apenas que a cauda da mensagem atual ainda está no segmento de consulta e não força mais expansão nem bloqueia a interação. Quando a mesma seção de Explore recebe novas subtools durante o streaming, a identidade do componente agregado e do estado de expansão deve ser ancorada na primeira subtool; é proibido colocar a última subtool ou a contagem atual na chave de identidade, para que o crescimento do conteúdo não redefina para recolhido um detalhe que o usuário já expandiu. Durante a execução o ícone continua fixo como lupa, sem troca por loading spinner. O `kindLabel` no estado recolhido sempre usa `Explore` / `查阅`, sem marca temporal, e não exibe mais `Exploring` / `Explored`; o corpo do resumo e o kind label são sempre separados por um ponto estático, e até no estado completo aparece `Explore · 3 lists, 2 files`. O `primaryText` / `secondaryText` só é emprestado quando o resumo da subtool mais recente já está definido. Os resumos de subtool sempre acrescentam o estado de ação com "ing", por exemplo `Explore · Reading 文件名 路径`, `Explore · Searching 查找 xxx`, `Explore · Running command`, sem sumir com a conclusão da subtool nem virar texto de conclusão. A subtool read só entra no estado recolhido depois que o caminho foi resolvido, e reutiliza o chip de arquivo da própria ferramenta Read, preservando ícone de arquivo, tooltip de caminho e comportamento de clique na pré-visualização do arquivo; é proibido que um fallback semiacabado como `Read` ocupe o resumo. Quando a subtool muda de running para completed, o estado recolhido mantém o conteúdo da subtool mais recente, evitando oscilar entre a palavra de status da subtool e as estatísticas agregadas do pai. A mudança de conteúdo no estado recolhido usa por padrão uma animação de rolagem vertical: uma rolagem de 300 ms, 500 ms de permanência estável após a rolagem antes de tocar a próxima, e duração total por item obrigatoriamente menor que 1 s; `ToolCallBlock.disableSummaryContentAnimation` / `AssistantMessage.disableToolSummaryContentAnimation` são interruptores unificados e desligam simultaneamente a rolagem de resumo de Agent e de Explore, exibindo diretamente o resumo mais recente e limpando a fila pendente; `ToolLayout.disableSummaryContentAnimation` ou `QueuedSummaryContent.disableAnimation` continuam como interruptores locais. A fila tem no máximo três itens, respectivamente o item atual, o segundo item pendente e o terceiro item que pode ser inserido; o item atual não é interrompido, o segundo não é sobrescrito por resumos posteriores, e novos resumos que chegam durante a animação apenas substituem o terceiro, evitando enfileirar resumos expirados indefinidamente. Se o timer de rolagem chegar visivelmente atrasado porque a main thread está ocupada, não se reproduz a fila antiga; comprime-se direto para o resumo mais recente, evitando continuar reproduzindo estados expirados após um travamento. Ao final do Explore, a fila pendente é comprimida no resumo agregado final, sem continuar reproduzindo resumos expirados de subtools. O estado expandido exibe as estatísticas agregadas do pai e o detalhe das subtools. O nó pai do Explore é apenas um container sintético de UI e não representa uma execução real de tool; a falha de uma subtool só é exibida no detalhe da própria subtool, e é proibido agregar o `error` de qualquer subtool em um estado de falha do Explore pai. A exibição de falha da própria ferramenta de protocolo real não é afetada por esta regra.
- Os estados em execução do pai de Explore e de Execute são derivados pelas fronteiras de fase: o pai só é `in_progress` quando o agrupamento está no último chunk de trabalho do assistant visível do segmento `running` e não há nenhuma outra row visível depois do grupo. Outras tools seguintes, texto do assistant ou reasoning visível encerram a fase anterior; reasoning não inicial definido como oculto, assim como rows de Shell adiadas por ainda não terem o comando, não constituem fronteira visível nem participam da verificação de posição final. A cauda do segmento terminal é completed (pode exibir stopped quando existe child cancelled). O ciclo de vida das subtools afeta apenas o detalhe expandido e não determina retroativamente o estado em execução do pai.
- A classificação dos comandos shell agregados no Explore deve cobrir simultaneamente Unix shell e Windows PowerShell. Comandos embrulhados em `pwsh` / `powershell.exe -Command` são desembrulhados antes da classificação; comandos PowerShell somente-leitura conhecidos como `Get-ChildItem` / `gci` / `dir`, `Get-Content` / `gc` / `type`, `Select-String` / `sls`, `Get-Location`, `Test-Path`, `Resolve-Path` entram no Explore; comandos de escrita ou destrutivos conhecidos como `Remove-Item` / `del` / `erase`, `Set-Content`, `Add-Content`, `Clear-Content`, `Out-File`, `New-Item`, `Move-Item`, `Copy-Item`, `Rename-Item`, `Set-Item` não entram no Explore. A classificação de escrita tem prioridade sobre a de leitura.
- O texto de command nos resumos de tool e nos detalhes de Execute herda uniformemente a UI sans, sem usar `font-mono`; a saída de comando continua com `font-mono`, mantendo o alinhamento e a legibilidade de dados terminal-like. Essa é a exceção de produto às regras globais padrão de typography para exibição de command.
- O grupo pai de Execute usa o título de categoria multiplataforma `Terminal` / `终端`, sem se referir a um aplicativo Windows Terminal específico; PowerShell, cmd.exe, Git Bash, WSL e Unix shell mantêm esse título, e o texto Running/Ran da subtool Execute individual permanece inalterado. O `kindLabel` e o resumo do grupo pai são sempre separados por `·` estático. Durante a execução, cada snapshot de rolagem deve conter a semântica de ação completa `Running <command>` / `执行中 <command>`, e não pode rolar apenas o command nu; a estrutura do resumo fica alinhada ao sub-resumo de shell do Explore: a palavra de ação usa `text-foreground-subtle`, o command usa `text-foreground-subtlest`, e ambos são tocados como um único snapshot de rolagem. Com o grupo pai expandido durante a execução, o summary pai mostra apenas `Terminal · N commands`, sem continuar exibindo a palavra de ação ou o command atual, sendo o estado atual expresso pelos summaries de subtool abaixo. No estado completo exibe `Terminal · N commands` e as estatísticas de falha/parada.
- Rows consecutivas de escrita de arquivo são agregadas em um grupo pai `Changes` / `更改`; o estado em execução do pai é, como em Explore/Terminal, determinado pelas fronteiras de fase visíveis, sem depender do ciclo de vida dos filhos. No estado recolhido em execução, rola verticalmente o mais recente `Writing/Editing + chip de arquivo + diretório relativo`; no estado expandido, em execução ou completo, exibe apenas `Changes · N files`; no estado recolhido completo exibe `Changes · N files · chips de arquivo`. Depois de aplanar arquivos entre filhos, a deduplicação é feita pelo path completo, preservando a primeira ordem; a lista completa é renderizada primeiro e, a partir da largura efetivamente disponível no summary, mantém o maior número possível de chips anteriores, mostrando `+N` para o restante, e recalcula via ResizeObserver quando a largura muda, restaurando ou recolhendo os arquivos. O summary multifile de um único Edit continua reutilizando o renderer de subfile existente. Changes é apenas um container sintético de UI, e falha/parada de filhos não é agregada em falha do pai.
- O nome de arquivo do chip de arquivo reutilizado nos summaries e no conteúdo rolante de Edit e Changes usa uniformemente `text-foreground-subtle`, um nível abaixo do texto principal comum; o diretório relativo que vem depois continua usando `text-foreground-subtlest`, preservando a diferença hierárquica entre nome do arquivo e caminho.
- As ferramentas Agent / SubAgent sempre usam o ícone de bot e o kind label externo SubAgent, e é proibido exibir o tipo de agent (por exemplo `Explore`) como kind externo; nem durante a execução o ícone de bot é substituído por loader. O corpo do resumo e o kind label no estado recolhido são sempre separados por um ponto estático, e até no estado completo aparece `SubAgent · xxx`. Quando existe um summary confirmável de subtool, o corpo do estado recolhido empresta o summary da subtool mais recente, por exemplo `SubAgent · Reading 文件名 路径`, `SubAgent · Searching 查找 xxx`, `SubAgent · Running command`; apenas o summary da subtool depois do ponto participa da animação de rolagem. O summary da subtool sempre mantém o estado de ação com "ing", sem sumir com a conclusão. O estado expandido continua exibindo o prompt do próprio Agent, o conteúdo ativo e a lista de subtools. Sem summary explícito de subtool, continua exibindo o título ou a descrição do próprio Agent.
- O estado visual em execução do SubAgent observa apenas o `pending` / `in_progress` da tool do Agent pai. As subtools são detalhe da área expandida e não mantêm viva retroativamente a execução do Agent pai; quando o Agent pai já está completed, mesmo que a subtool ainda esteja running, o externo converge para o `SubAgent · xxx` estático.
- Ao encontrar uma subtool `TodoWrite` no estado recolhido de Agent / SubAgent, exibe-se um resumo semântico de pendências, e não o nome cru da tool: mostra-se primeiro o item in-progress, senão o próximo item não concluído, senão o último item concluído; o formato é `Updating todo 2/5 · 当前任务`, e quando tudo está concluído `Updated todo 5/5 · 当前任务`. Assim, quando o subagent atualiza o plano, o summary rolante ainda consegue expressar o conteúdo concreto, em vez de `Running TodoWrite`.
- Enquanto o turno principal atual ainda está running, o card de Agent / SubAgent e o `ChatLoading` do rodapé do chat são exibidos simultaneamente. O card de Agent e suas subtools internas respondem apenas pelo detalhe da tool e não controlam o `ChatLoading`; o loading do rodapé é ocultado quando o turno principal entra em estado terminal, e também é ocultado enquanto se aguarda AskUserQuestion ou confirmação de permissão, evitando expressar "aguardando o usuário" como "pensando".
- Durante o streaming, a tool shell em execução é tratada em dois cenários:
  - Quando `tool_input_start` acabou de chegar e o argumento de comando ainda está incompleto, não se renderiza esse shell ainda não classificado. Seja ele uma tool subsequente de um Explore ativo, ou a primeira tool independente do turno atual, só exibe-se quando o comando estiver classificável, evitando que o usuário veja `Run` e no frame seguinte a tool seja promovida a `Explore` por ser um comando somente-leitura.
  - Um shell não classificado que vem logo após um Explore ativo, mesmo já concluído, não é exibido isoladamente como `Ran Bash`. Essa tool não tem comando a exibir e deve ser absorvida pelo progresso visual do Explore anterior, evitando sobras de linhas Bash sem sentido abaixo do resumo do Explore.
  - Quando o comando já é classificável, renderiza-se imediatamente conforme o resultado da classificação: comandos de sondagem somente-leitura entram no `Explore`, e comandos que não são de sondagem permanecem como `Run` / shell tool independente, evitando que comandos realmente executados fiquem sem feedback de progresso.
- A ferramenta `Goal`, o mention do comando `/goal` nas mensagens do usuário, o resumo de goal e a linha divisória de validação de goal usam uniformemente o `GoalIcon` do lucide.
  Esse ícone é consistente com a semântica visível ao usuário de `/goal`, evitando continuar usando `TargetIcon` e causar inconsistência entre os ícones do projeto e o ícone `goal` do lucide.

## Contagem de linhas editadas

- O summary de `Edit` / ferramentas de escrita de arquivo continua reutilizando `changeStat.added` / `changeStat.removed` como única fonte de estatística, e a UI não rededuz a contagem de linhas de diff na camada de renderização.
- Quando o número de linhas muda, o número em `+N` / `-N` pode usar uma animação de troca de página de caractere curta; os símbolos `+` / `-` permanecem estáticos, e as cores continuam usando `text-diff-added` / `text-diff-removed`.
- A animação de troca de página deve usar largura de caractere fixa e `tabular-nums`, evitando tremidas na linha de resumo durante atualizações contínuas de streaming no desktop ou durante a reposição de quadros na recuperação replayable do celular.
- Quando o usuário habilita `prefers-reduced-motion: reduce`, o número degrada para um slot de caractere estático, mantendo apenas o rótulo de tecnologia assistiva com a leitura completa.
- A pré-visualização de `Write` / `Edit` em execução é alimentada pela projeção com no máximo um novo `changeStat` real por segundo; path, conteúdo, diff e `+N/-N` do mesmo ponto de amostragem devem ser atualizados atomicamente.
- A UI é proibida de usar `requestAnimationFrame` para perseguir o valor alvo linha a linha. Quando o alvo muda de `12` para `45`, entregue-se `45` diretamente em uma única troca curta, sem reproduzir valores intermediários como `13` e `14`.
- Quando a ferramenta termina, é cancelada, um snapshot histórico é restaurado ou o celular replayable entra em estado terminal, exibe-se imediatamente o alvo real, sem reproduzir contagens de linhas de streaming já expiradas.

## Consistência histórica

- O tool call persistido do ZCode agora persiste `status` e `raw`
- Assim, o diff / image / payload de tool especial do fluxo ao vivo ainda pode reutilizar a mesma lógica de exibição após a atualização
- O `ToolResultDisplayPayload` do Core é a fronteira de fato estruturado da UI: o display é gerado a partir do output original da tool, transmitido via `ToolCallResult.result.display` em tempo real e persistido via completed tool part metadata. A formatação, o truncamento e o hook additional context do content visível ao modelo não podem alterar o display.
- A projeção de produto da V4 deve manter displays genéricos como CUA e file diff em `ToolCallRow.output.display`; `ToolCallRow.display` mantém apenas o canal dedicado existente `node_repl_images`. O adapter da UI lê preferencialmente `output.display`, com compatibilidade para o display de topo do Node REPL antigo.
- O `input` do CUA display v1 continua legível apenas como campo de compatibilidade para registros históricos antigos; novos eventos não o escrevem novamente. O `ToolCallRow.input` da própria chamada de ferramenta é a única fonte de verdade da entrada, e a UI descarta a cópia contida no display antigo ao fazer o parse.
- A leitura de display pela UI deve cobrir simultaneamente o raw event ao vivo do desktop `desktop-continuous` e o metadata persistido do celular `web-remote-replayable`; não é permitido emendar dados de recuperação replayable no fluxo principal desktop continuous nem contornar as fronteiras existentes de recuperação de snapshot/gap.
