### D01: o envio remoto deve esperar a configuração de modelo mais recente

Commit original f0edfd69cf. Não é um novo conjunto de configuração de modelo: a intenção era evitar que o Agent remoto em reinício perdesse o Registry em memória, ou que, antes de a sincronização pós-gravação terminar, um envio imediato não encontrasse o modelo. O código antigo sincronizava antes de executar comandos como envio, compact, retry e fork, e só então entregava ao Agent; excluindo explicitamente o celular replayable.

```text
atual: conectar/gravar -> sincronização em nível de Environment (execução independente)
      clicar em enviar -> submeter a Selection atual -> o Host de destino executa ou recusa conforme o Registry daquele momento

se recuperar: clicar em enviar -> esperar a sincronização da configuração atual do Environment de destino terminar -> submeter a mesma Selection
                    falha de sincronização -> mostrar erro, manter o rascunho, não enviar
```

Hoje não é totalmente sem sincronização: já existem barreiras de conexão, gatilhos por gravação/conta/modelo default, coalescência no mesmo Environment e refresh trailing. Mas isso não garante que cada envio espere a sincronização mais recente. O usuário antes aceitou explicitamente essa pequena janela de tempo e depois afirmou que sim, é possível recuperar, então está pendente de nova confirmação.

Se for necessário recuperar, sugiro adicionar apenas a capacidade de espera pelo Environment de destino ao coordenador de sincronização existente; não é possível reenviar o antigo RuntimeModel pelo Renderer, nem repetir a sincronização por Workspace. O coordenador atual não expõe uma interface pública para esperar o sucesso de uma dada geração, e após estar conectado a falha é tratada como degradação; é preciso distinguir claramente "espera terminou" de "sincronização teve sucesso". Esta rodada não acrescentou esse comportamento por conta própria.

### D02: trocar o pacote de conta substitui automaticamente o modelo de sessões existentes

Commit original 6ce53c6ec4. A intenção era que, quando o usuário passasse de um Start expirado para um pacote pessoal, as sessões antigas não exibissem mais nem solicitassem o Start expirado; a implementação antiga observava o estado da Family e enviava automaticamente um comando de troca de modelo para aquela sessão.

```text
atual: a conexão de conta muda -> o Registry é atualizado -> se a escolha original ficar inválida, fica vazia e o usuário reseleciona
se recuperar: a conexão de conta muda -> seleciona um modelo/nível substituto dentro do novo pacote -> reescreve a escolha da sessão existente
```

Não é só acrescentar uma chamada: é preciso decidir como tratar modelo substituto, reasoning, rascunho não enviado e sessão em execução. Isso conflita de verdade com a decisão anterior de "escolha inválida fica vazia, sem troca silenciosa de modelo". Sugere-se manter o estado atual; se o usuário quiser acompanhamento automático, o escopo aplicável precisa ser definido explicitamente, sem restaurar o fallback implícito do helper de Family antigo.

Atenção: 1ccf6f906e não pertence inteiramente a este item: seu banner de erro de envio, preservação de rascunho e limpeza de erro ao trocar de Session já existem no SessionPane atual; o "escolher Start mas enviar Coding" que ele corrigia está a cargo da resolução centralizada para a conexão atual em R08. Esses dois pontos não precisam esperar a decisão de D02 e não podem ser perdidos só porque os commits relacionados estão misturados.
