# Visualizador de trajetória de chamadas de modelo (Model Trajectory Viewer)

> O catálogo de comportamentos E2E e o status de cobertura estão em
> [`docs/testing/model-trajectory-e2e-coverage-matrix.md`](./testing/model-trajectory-e2e-coverage-matrix.md).

Adiciona «Ver trajetória da chamada» ao menu de contexto da task / ao menu «mais» do Header, visualizando de forma profissional e legível, na barra lateral direita, todo o processo de chamadas de modelo de uma task/session: distinguindo os papéis system / user / assistant / tool, exibindo para cada chamada o modelo, o consumo de tokens, a latência, o finishReason, os argumentos das chamadas de ferramenta e seus resultados, pilhas de erro, etc.

## Origem dos dados

- Os arquivos `model-io-*.jsonl` em `~/.zcode/cli/debug` (modo de desenvolvimento) e `~/.zcode/cli/rollout` (modo de produção, mantendo no máximo os 3 arquivos de sessão mais recentes).
- Escritos em disco por `apps/zcode-cli/packages/adapters/src/model/runner-debug.ts`, com nomes no formato
  `model-io-<sanitizedSessionId>.jsonl`. Uma session corresponde a um único arquivo JSONL; o primeiro registro guarda o
  `request.messages` completo, e as chamadas de modelo seguintes guardam apenas o delta de mensagens novas em relação à anterior, evitando repetir o contexto completo a cada rodada.
  Cada registro traz `sessionId` / `turnId` / `traceId` / `querySource`, `request` (messages / toolNames),
  `response` (text / reasoningText / toolCalls / usage / finishReason) e `error`. O `response.reasoning` devolvido pelo AI SDK
  precisa ter o texto extraído por ordem de blocos de reasoning antes de ir para o disco, unido por linhas em branco como
  `response.reasoningText`; as quebras de linha dentro dos blocos são preservadas. Sem texto de reasoning válido, o campo é omitido, evitando criar linhas vazias de «processo de pensamento».
  `querySource` e `model.role` servem para distinguir requisições da sessão principal, geração de título, compact, subagent etc.;
  em logs antigos sem `querySource`, a camada de serviço faz reconhecimento de compatibilidade dos prompts conhecidos de geração de título.
- O `content` das mensagens TOOL no model-io real costuma ser uma string, enquanto `toolCallId` / `toolName` ficam no nível superior da mensagem;
  ao normalizar para `tool-result`, a camada de serviço precisa preservar também esses campos de correlação de nível superior, não apenas mapear o output, senão a UI não consegue correlacionar e exibir o tool call ID.
- O caminho de escrita precisa ser limitado: escrever o model-io depois que a requisição do modelo termina é um desvio de diagnóstico no fluxo principal do agent, e é proibido ler e expandir de forma síncrona todo o histórico JSONL para acrescentar um novo registro. Sessões longas já chegaram a escrever um único arquivo de rollout de produção na casa de 1GB, e a implementação antiga, antes de cada escrita, fazia
  `readFileSync(filePath, "utf8")` e fazia `JSON.parse` / expand linha a linha, o que podia disparar um native crash nas etapas de conversão UTF-8 ou de alocação de strings no V8, causando a saída direta do subprocesso do agent sem que os logs JS comuns tivessem tempo de ir para o disco.
- A nova implementação usa apenas o resumo da requisição anterior no processo para determinar o delta; em caso de reinício do processo, cache ausente, histórico incompatível ou arquivo acima do hard limit de produção, escreve o baseline limitado da requisição atual (mantendo apenas as mensagens mais recentes do tail, se necessário) e continua acrescentando deltas a partir desse baseline. O rollout de produção é uma «trajetória recente e limitada», sem promessa de replay completo e infinito; o debug de desenvolvimento retém mais campos originais, mas também não pode reler o arquivo histórico inteiro na escrita.
- O ZCode Agent trata `taskId` como `sessionId` (veja as várias ocorrências de `sessionId: params.taskId` em `zcodeTaskServiceAdapter`),
  portanto a trajetória lê apenas `model-io-<sanitizedTaskId>.jsonl`, com correspondência exata por `record.sessionId === taskId`.
  Apenas o ZCode Agent (glm) grava o model-io.
- O caminho de leitura também precisa ser limitado e assíncrono: o Host lê por blocos a partir do final do arquivo, varrendo no máximo 32 MiB e mantendo apenas os `limit` registros mais recentes; é proibido usar `readFileSync + split` para carregar o JSONL inteiro de forma síncrona. Se o ponto inicial da varredura cair no meio de um registro, a linha residual é descartada; se o arquivo não puder ser lido, há degradação para resultado vazio. O log de desenvolvimento registra os bytes varridos e o tempo decorrido, facilitando localizar arquivos anormalmente grandes e evitando que informações de diagnóstico de alta frequência entrem no log de produção.

## Camadas e arquivos principais

Camada de serviço (leitura de disco no host; desktop lê a máquina local, controle remoto pelo celular lê o host remoto, a UI apenas consome resultados estruturados):

- `packages/services/src/session/zcodeTaskService.ts`: novos tipos `ZCodeModelTrajectory*` e
  `IZCodeTaskService.getModelTrajectory({ taskId, limit })`.
- `packages/services/src/zcode-agent/modelTrajectory.ts`: lê de forma assíncrona e limitada a cauda do arquivo único da session, reconstitui as mensagens delta,
  normaliza messages / parts / toolCalls / usage, ordena por `startedAt` e, acima do `limit` (padrão 200), mantém as N mais recentes.
- `packages/services/src/zcode-agent/zcodeTaskServiceAdapter.ts`: implementa `getModelTrajectory`.

Camada de UI:

- O conteúdo da chamada não exibe os títulos de seção `INPUT` / `OUTPUT`; as linhas das mensagens de entrada e o título de saída `ASSISTANT` são dispostos direto na ordem dos dados, reduzindo níveis verticais sem informação.

- Entrada: `TaskActionMenuContent.tsx` ganha o item «Ver trajetória da chamada», integrado em dois pontos via `TaskListItemContextMenu` →
  `TaskListItem` (lista de tasks) e `WorkspaceHeaderSections` (Header).
- Ponte: store singleton `store/modelTrajectoryStore.ts` + `hooks/useModelTrajectoryOpenBridge.ts`.
  O menu, bem ao fundo, dispara o pedido «abrir trajetória» pelo store; o `useAppPanels` do workspace de destino assina e, após casar por `workspaceKey`, abre a tab da barra lateral, evitando atravessar callbacks por toda a árvore da lista de tasks e evitando que instâncias de múltiplos workspaces abram em cruz.
- Tab da barra lateral: `lib/workspaceSidePane.ts` ganha o tipo de tab `model-trajectory` e `openModelTrajectorySidePane`;
  `app-shell/AnimatedSidePanePanel.tsx` renderiza `ModelTrajectoryPane`;
  `app-shell/SidePaneTabTrigger.tsx` / `SidePaneTabOverview.tsx` ganham ícone e título.
- Visão: `ModelTrajectoryPane.tsx` + `ModelTrajectoryPaneParts.tsx`, com dados vindo de `hooks/useModelTrajectory.ts`.
  A área de conteúdo da trajetória usa um contêiner de rolagem vertical nativo, e não o Radix `ScrollArea`; evita-se a camada de packaging de conteúdo que ele insere automaticamente com
  `min-width: 100%; display: table`, que faria conteúdo longo de trajetória participar de um cálculo de largura anormal.
- O invólucro `ResizablePanel` do Side Pane precisa usar `!overflow-hidden` para sobrepor o `overflow:auto` inline injetado por `react-resizable-panels`; não se deve deixar o invólucro do painel e o conteúdo da tab formarem rolagem vertical ao mesmo tempo; cada tab mantém sua própria área de rolagem de conteúdo, e a trajetória de chamadas rola apenas pelo contêiner nativo `overflow-y-auto` de `ModelTrajectoryPane`.

## Modelo de exibição

Cada registro de model-io é «uma chamada de modelo». A visão organiza a trajetória cronologicamente na cadeia
**entrada (user / resultado de tool) → saída (texto do assistant / reasoning / chamadas de ferramenta)**:

- A primeira chamada exibe o contexto inicial completo (system + user inicial).
- As chamadas seguintes da sessão principal exibem apenas as mensagens não-assistant adicionadas em relação à anterior (o assistant é apresentado pelo Output da anterior), evitando repassar o histórico.
- Requisições sidecar como geração de título, compact e prompt enhance exibem seu próprio prompt completo, sem aplicar o delta da sessão principal.
- O cabeçalho resume o número de chamadas, o total de tokens e os modelos usados; o cabeçalho de uma linha de cada cartão de chamada exibe a origem, o finishReason, tokens in/out, a latência e o horário.
- O cabeçalho de cada cartão de chamada mostra um badge de origem (como «sessão principal», «geração de título», «compressão de contexto», «subagente»).
- Além do texto de exibição localizado, o título de origem e o pill de finish reason devem expor, respectivamente, os atributos semânticos estáveis
  `data-trajectory-source-kind` / `data-trajectory-query-source` e
  `data-trajectory-finish-reason`. O E2E usa esses atributos para validar a projeção da trajetória e não deve tratar o texto de exibição em inglês
  como contrato funcional; os textos de internacionalização são validados por asserções representativas com locale explícito e fixo.

## Layout compacto e interação

- A trajetória adota um log de chamadas em coluna única, sem múltiplos níveis de cartão: cada chamada é composta por uma linha de resumo e detalhes expansíveis sob demanda; entre as chamadas há apenas um
  separador independente `h-px bg-border`, sem border no contêiner; a lista não define padding externo nas quatro bordas, e a linha divisória encosta na borda do painel.
- O cabeçalho do painel e o cabeçalho de resumo de cada chamada usam `px-3 py-2`, mantendo número, título, tags e metadados compactos e com espaçamento consistente.
- O resumo da chamada usa uma estrutura de linha única: à esquerda «número + título de origem + pill de finish reason semântico», à direita alinhado à direita em `IN {inputTokens} · OUT {outputTokens} · latência · horário`.
  Cada chamada deixa de repetir o pill de modelo e o attempt; o conjunto de modelos permanece no cabeçalho de visão geral do painel. O título de origem e o pill de finish reason devem ficar adjacentes, e o espaço elástico restante fica entre o pill e as métricas à direita;
  em uma barra lateral estreita o título de origem é truncado primeiro, mantendo as métricas à direita completas.
- A origem da chamada usa `text-ui-sm font-medium text-foreground`; o motivo de término semântico usa
  pill `bg-tag border-border text-ui-xs`, e o número sequencial e os metadados à direita usam `text-ui-xs`.
- O número sequencial usa caixa de linha `size-5` centralizada horizontal e verticalmente, alinhada ao título e ao pill, sem seguir a centralização do resumo de duas linhas.
- A linha de resumo de cada chamada fica fixa no topo durante a rolagem do conteúdo da trajetória, usando fundo `surface` semitransparente, desfoque leve de fundo e linha inferior `border-border/50`, garantindo que o título continue legível quando o payload passa por baixo.
- Os grandes níveis IN / OUT de cada chamada ficam sempre expandidos, sem interação de recolhimento da chamada inteira; apenas mensagens específicas e payloads mantêm um segundo nível de dobra.
- A área de ações do cabeçalho do painel oferece um único botão de alternância «expandir tudo / recolher tudo» à esquerda de «abrir diretório de origem», exibido apenas quando existem registros de trajetória. O ícone reaproveita `Maximize2 / Minimize2` da lista de tasks, usando `size-3.5 text-foreground`. Como todas as linhas de mensagem são inicializadas expandidas, a ação inicial é recolher tudo, e após o disparo a ação do botão passa a ser expandir tudo; cada ação em massa sincroniza todas as linhas de mensagem atuais sobrescrevendo-as por meio de um command version incremental. A linha individual continua podendo alternar de forma independente, sem reescrever para trás a próxima ação do botão em massa. O estado padrão é inicializado diretamente pelo command compartilhado e pelo lazy state dentro da linha, sem disparar uma segunda atualização por `useEffect` em cada linha.
- À esquerda de «expandir tudo / recolher tudo» há um menu personalizado de expansão. O menu lista seis categorias de conteúdo na ordem System, User, Reasoning, Assistant, Tool Call, Tool Result, usando um Switch `sm` à direita para expressar o estado de expansão alvo daquele tipo; clicar na linha inteira ou no Switch atualiza apenas aquele tipo, e o menu permanece aberto para configuração contínua. Expandir/recolher tudo atualiza os seis switches de forma sincronizada. Comandos de tipo e comando global compartilham uma version monotônica crescente, e o comando posterior sobrescreve o override antigo de linha do tipo correspondente; tipos não atingidos por este comando de tipo mantêm seu estado. O menu e todos os textos devem ser internacionalizados.

```text
Header toggle
    ├─ expand all   -> command(open=true, version+1)  ┐
    └─ collapse all -> command(open=false, version+1) ┴─ row render 直接读取最新 command

row trigger -> local override(open, current command version) -> only that row changes
next header command(version+1) -> supersedes every older local override
```

Comandos em massa não devem ser sincronizados por `useEffect` de cada linha para o state local `open`, senão N mensagens acrescentam N escritas de estado e uma segunda rodada de commit após a atualização de contexto. Cada linha deve, na fase de render, comparar a version do comando em massa com a version do override local e derivar diretamente o `open` desta vez; a operação de linha registra a command version atual, e o próximo comando em massa de version maior a sobrescreve naturalmente.

- O conteúdo expandido é dividido por `IN` / `OUT`. system, usuário, tool, assistant, reasoning e as mensagens de tool call/result começam todas expandidas, em coerência com a ação inicial do cabeçalho «recolher tudo»; após clicar numa linha, ela pode ser recolhida no mesmo nível para uma pré-visualização de linha única, e ao expandir novamente mostra diretamente o texto completo, o processo de pensamento, a entrada da ferramenta ou o resultado da ferramenta, sem um segundo nível de dobra aninhado dentro do conteúdo expandido.
- A área externa do conteúdo da chamada usa `p-2 gap-y-2`, fornecendo uniformemente padding interno de 8px nas quatro bordas e espaçamento de 8px entre grupos grandes adjacentes; INPUT / OUTPUT são cada um um cartão de grupo grande independente, usando `overflow-hidden rounded-lg border border-card-border`, sem margin nem cor de fundo próprios. As linhas de mensagem ficam em sequência dentro do cartão, com o layout controlado pelas próprias seções e linhas de mensagem.
- As seções `INPUT / OUTPUT` exibem cada uma sua linha de título independente, usando `h-8 px-3 bg-surface text-ui-sm font-mono uppercase text-foreground`, criando hierarquia em relação ao zebra `bg-surface/30` das mensagens. O título não exibe linha colorida à esquerda nem ícone decorativo e não define `mt-*` nem `mb-*`; os dois grupos usam o mesmo estilo neutro e servem apenas para expressar o agrupamento de requisição e de produção, não participando do zebra das linhas de mensagem.
- Entre linhas de mensagem adjacentes não há gap; entre os títulos INPUT / OUTPUT e a primeira mensagem, e entre mensagens adjacentes, insere-se um elemento separador independente `col-span-full h-px bg-border/50`, sem usar a border da própria linha de mensagem.
- A lista inteira da trajetória compartilha um grid externo de três colunas `max-content minmax(0, 1fr) auto`; cada Call Card, a área de conteúdo da chamada, as áreas de entrada e saída e as linhas de mensagem herdam, via `subgrid`, o mesmo conjunto de trilhas de coluna «papel / conteúdo / ação», de modo que a largura da primeira coluna é determinada pelo rótulo de papel localizado mais longo de toda a lista, como em uma table. O grid usa `gap-x-2`, apertando o espaçamento entre o conteúdo e o Chevron para 8px; o rótulo de papel usa adicionalmente `pr-1`, mantendo o espaçamento visual entre papel e conteúdo em 12px. Não é permitido que Call Cards diferentes ou as saídas Input / Assistant de assistant calculem a largura da coluna de papel separadamente, nem usar uma coluna de papel de largura fixa que gere grandes espaços em branco depois de rótulos curtos. A coluna de conteúdo deve permanecer `minmax(0, 1fr)`, garantindo que resumos longos ainda possam encolher e ser truncados normalmente.
- A coluna de ações compartilhada tem a largura definida apenas pelo Chevron; a coluna de ações usa `-ml-1 mr-1`, mantendo inalterado o espaçamento entre as colunas de papel e de conteúdo, mas apertando de 8px para 4px o espaçamento visível entre o conteúdo ou o pill de tool ID e o Chevron. O botão de copiar do estado expandido usa `absolute right-full mr-1` à esquerda do Chevron, sem alargar a coluna de ações compartilhada. Os metadados do estado expandido usam `mr-7` para reservar com precisão «botão de 24px + 4px de espaçamento», evitando que o ícone de cópia cubra a data e hora; linhas recolhidas não reservam esse espaço. O Chevron de todas as linhas encosta sempre na mesma linha de borda direita, sem deixar um vão à direita da seta.
- A coluna de ações da linha de título mantém apenas o Chevron; quando qualquer linha expande ou recolhe, o summary, as tags e o Chevron das outras linhas não podem saltar horizontalmente.
- O papel `tool` nas entradas do modelo é exibido como `Tool result` em inglês, «工具结果» em chinês, claramente distinto de `Tool call` / «工具调用» nas saídas do assistant.
- Os textos de papel em chinês usam nomes semânticos completos: system é «系统提示词», user é «用户消息», e texto comum de assistant é «助手消息»; não se usam rótulos curtos como «系统 / 用户 / 助手», que se confundem com agrupamento ou identidade de produto.
- O pill de nome de ferramenta não tem largura máxima nem truncamento e deve aparecer por completo; o Tool call ID remove o prefixo inicial `call_` na exibição da interface, mantendo o ID original nos dados da mensagem. Quando o espaço é insuficiente, prioriza-se comprimir o summary; o pill de Tool call ID ainda pode ser truncado para proteger a barra lateral estreita e o layout Web no celular.
- As linhas recolhidas de Tool Result e Tool Call exibem explicitamente, antes do summary, uma etiqueta de direção de dados com largura adaptada ao conteúdo: Tool Result usa `OUTPUT` («输出»), e Tool Call usa `INPUT` («输入»). A etiqueta de direção usa `text-ui-sm` com a cor do texto principal e encolhe conforme a largura real do texto, seguida do ícone de seta para a direita em uma cor de terceiro nível textual com espaçamento compacto padrão, e então o summary de nível secundário; não é permitido usar largura fixa criando um vão entre rótulos curtos em chinês e a seta. Após expandir, o summary e a seta para a direita são ocultados simultaneamente; a etiqueta de direção permanece e não é repetida no corpo expandido.
- Os títulos de seção da área de conteúdo, os rótulos de papel, as prévias de mensagem, o corpo, o pensamento e o conteúdo de ferramenta usam uniformemente `text-ui-sm`; o número sequencial, os pills e os metadados do cabeçalho de resumo da chamada continuam em `text-ui-xs`.
- Se o output de Tool Result for `{ type: "error-text", value: string }`, o summary recolhido e o corpo expandido devem usar diretamente o `value`, sem serializar o objeto de wrapper de erro como JSON. O summary recolhido continua colapsando espaços em branco consecutivos, enquanto o corpo expandido preserva as quebras de linha originais do texto de erro.
- Quando o output do Tool Result ou o input do Tool Call for `error-text`, a linha recolhida exibe `CircleAlertIcon` antes de INPUT / OUTPUT, e o ícone e a etiqueta de direção usam a cor destrutiva de erro; payloads de ferramenta comuns não exibem esse estado. O payload de erro expandido usa o contêiner de erro sem borda `rounded-lg bg-destructive/10` com a cor de texto destrutiva envolvendo-o; o nome da ferramenta, o ID da chamada, a cópia e o comportamento de expansão por overflow permanecem inalterados. No model-io padronizado, o `isError` / `is_error` de nível superior das mensagens TOOL de tipo string deve ser restaurado para `{ type: "error-text", value: content }`, e o estado de erro não pode ser perdido no mapeamento da camada de serviço.
- system, user e tool reutilizam o mesmo layout de mensagem transparente que ocupa toda a largura disponível. O summary recolhido de system pega a primeira linha não vazia; o summary recolhido de user, de mensagens comuns de assistant e do processo de pensamento lê o texto completo colapsando espaços em branco consecutivos como quebras de linha em um único espaço; o summary recolhido de tool pega o conteúdo completo de `tool-result.output` e o comprime em linha única do mesmo modo, sem usar o nome da ferramenta como resumo. Todos os summaries são truncados dentro de uma única linha, com o Chevron na extremidade direita; à direita do summary de tool, dois pills outline independentes mostram `toolName` e `toolCallId`, e quando um campo individual está ausente apenas o pill correspondente é ocultado. Ao expandir, o cabeçalho oculta o summary, a seta de direção para a direita e os pills `toolName` e `toolCallId`, mantém a etiqueta de direção e exibe «latência desta chamada · data e hora completas»; os pills de nome e ID vão para a primeira linha do topo do conteúdo expandido, e o payload começa na linha seguinte. O datetime ISO completo é preservado em um tooltip. O que é exibido aqui é o `durationMs` / `startedAt` da chamada de nível model-io, e não a latência ou o horário da mensagem individual. O contêiner do botão Chevron usa `size-5` e o ícone usa `size-3`. Linhas expandidas exibem à esquerda do Chevron o botão de cópia `icon-sm ghost`, ocultado quando recolhido; a cópia usa os dados originais completos. No corpo expandido, system / user mostram a mensagem completa e tool mostra o payload completo, sem repetir o título «工具结果/工具调用». O corpo é exibido como conteúdo comum dentro do contêiner, sem fundo de cartão, raio ou margem externa; por padrão usa `max-h-64 overflow-hidden`, sem rolagem interna. Quando o conteúdo passa de 256px, uma máscara CSS de fade de 72px é adicionada na parte inferior, com uma cápsula «展开» flutuante `sm outline` centralizada horizontalmente em `bottom-3 left-1/2`; essa pílula usa `bg-surface/90` como fallback quando não há backdrop-filter, e troca para o fundo de vidro gaussiano `bg-surface/70 backdrop-blur-md` quando suportado. O corpo com overflow usa `pb-14` reservando espaço, mantendo o espaçamento padrão entre a última linha do corpo e o botão flutuante; sem a ação de overflow usa apenas `pb-2`. Após expandir, a altura máxima e a máscara são removidas e o botão centralizado passa a dizer «收起»; expandir afeta apenas a mensagem atual, e ao recolher a linha de mensagem volta ao estado com altura limitada.
- A saída de assistant deixa de usar o título de agrupamento `ASSISTANT` ou cartões de surface aninhados. O processo de pensamento, as mensagens de assistant e cada tool call de assistant são renderizados diretamente como linhas de mensagem independentes no grid compartilhado, com o mesmo summary de linha única, expansão de linha inteira, truncamento por overflow e ações de cápsula flutuante usados por system / user / tool result. Quando recolhido, um tool call de assistant serializa `toolCall.input` como summary compacto de linha única, exibindo o nome da ferramenta e o tool call ID em dois pills outline independentes, evitando repetir o summary e a tag de nome da ferramenta; ao expandir, exibe apenas o input completo formatado, com corpo transparente e com quebra de linha, sem repetir o título «输入», o título de chamada de ferramenta, cartão de fundo ou raio.
- Como as linhas recolhidas de `INPUT > TOOL` e `OUTPUT > ASSISTANT > Tool` já carregam o nome da ferramenta (Assistant Tool carrega também o ID), a área expandida não deve renderizar novamente o título «工具结果/工具调用 + nome da ferramenta + ID», mantendo apenas o cartão de payload válido de Output ou Input.
- O Chevron à direita do summary da mensagem usa `ml-1.5`, mantendo 6px de espaçamento de controle com a tag de ferramenta ou a prévia da mensagem.
- O cartão expandido usa `p-3` na camada externa, com 12px de espaçamento uniforme nas quatro bordas.
- Após a remoção da linha vertical à esquerda, título, linhas de mensagem e corpo expandido voltam a ter 12px de padding à esquerda: título e corpo usam `px-3`, a área de trigger da mensagem usa `pl-3` e tem o espaço à direita controlado pela coluna de ações independente; o corpo expandido usa `pt-0 pb-14` ou `pt-0 pb-2` conforme o estado de overflow. O texto e o payload de ferramenta do corpo expandido aplicam `trim()` apenas na exibição, removendo espaços no início e no fim mas preservando as quebras de linha do meio; a cópia continua usando os dados originais não aparados.
- Linhas de papéis de mensagem como system / user / assistant usam uniformemente `min-h-8` (mínimo de 32px), com o rótulo de papel à esquerda e o conteúdo à direita centralizados verticalmente na primeira linha; conteúdo expandido ou de múltiplas linhas pode crescer naturalmente.
- As cores usam estritamente os tokens semânticos de `DESIGN.md`: fundo principal `background`, estado expandido `selected`,
  camada de conteúdo `surface` / `card`, linhas divisórias `border` / `card-border`, usando `destructive` apenas em estados de erro reais.
- O `record.error` de nível de chamada de modelo é exibido depois do INPUT / OUTPUT do Call Card correspondente, usando fundo de erro semitransparente `bg-destructive/10`, sem borda, com `rounded-lg`; à esquerda usa `CircleAlertIcon` (`size-4 text-destructive`) alinhado com a primeira linha do título, com o nome do erro e a mensagem em `text-destructive`, e o stack no mesmo color com hierarquia atenuada. O bloco de erro não deve usar contorno nem fundo de surface comum.
- Os papéis são distinguidos principalmente por rótulos de texto compactos, sem camadas de fundo de grande área diferentes para system / user / assistant / tool.
- As linhas de mensagem não exibem linha vertical à esquerda; SYSTEM usa a cor de texto secundária `text-foreground-subtle`, USER usa o azul `--color-trajectory-user`, ASSISTANT usa o verde-azulado `--color-trajectory-assistant`, o processo de pensamento usa o roxo `--color-trajectory-reasoning`, TOOL CALL usa o âmbar `--color-trajectory-tool-call` e TOOL RESULT usa o azul-ciano `--color-trajectory-tool-result`. Os rótulos de papel coloridos usam uniformemente o `/80` do token dedicado; os cinco tokens dedicados precisam definir separadamente os valores padrão Light, Dark, Zai Light e Zai Dark, sem tomar emprestadas as cores de estado success, warning ou destructive. O processo de pensamento continua reaproveitando a resumo de linha inteira do USER, o clique para expandir, o limite de altura do corpo, a cópia e a estrutura «展开/收起», sem usar um cartão independente.
- Todas as linhas de mensagem de entrada e saída dentro do mesmo Call Card usam numeração sequencial contínua para desenhar o zebra, sem reiniciar a contagem entre a entrada e a saída do Assistant. A primeira linha permanece transparente e as linhas alternadas usam `bg-surface/30`; o conteúdo expandido herda o fundo da linha de mensagem à qual pertence, e o cabeçalho da chamada e as linhas divisórias não participam da alternância; as linhas de mensagem não recebem fundo de hover nem transição de cor.
- Barra lateral estreita e Web no celular mantêm estrutura de coluna única; payloads técnicos precisam quebrar linha e não podem alargar o painel, e as ações em cápsula flutuante podem permanecer compactas em larguras estreitas.

## Virtualização de listas longas

### Busca de conteúdo

- A área de ações do cabeçalho oferece um botão de busca à esquerda de «expansão personalizada»; ao clicar, exibe uma barra de busca embutida abaixo das estatísticas da chamada, contendo campo de entrada, `atual/total`, anterior, próximo e botão de fechar. Ao abrir, o foco vai para o campo; Enter avança, Shift+Enter retrocede, Escape fecha, sem sobrescrever o `Cmd/Ctrl+F` global do aplicativo.
- A busca indexa apenas, dentro da UI, a projeção de trajetória já carregada, sem criar nova API de servidor, RPC, campo de protocolo ou persistência. O escopo inclui system, user, o corpo de reasoning e assistant, o input de Tool Call, o output de Tool Result, o nome da ferramenta e o ID visível sem o prefixo `call_`; horário, tokens, modelo e rótulos de papel não participam. A correspondência é uma busca literal insensível a maiúsculas/minúsculas, e espaços em branco consecutivos na consulta e no corpo são tratados uniformemente como um único espaço, preservando o offset do texto original para o destaque.
- Ocorrências normais já montadas usam `--color-find-highlight`, e a ocorrência atual usa `--color-find-highlight-active`. Se a ocorrência atual estiver em uma mensagem recolhida ou na área de corpo com altura limitada, o estado de reveal da busca precisa forçar temporariamente a expansão da mensagem e do corpo completo; esse estado não pode ser gravado no override de expansão do usuário, e ao trocar de resultado, limpar ou fechar a busca volta ao estado anterior à busca, mantendo intacto o conteúdo que o usuário havia expandido manualmente.
- O posicionamento da lista virtual tem duas fases: primeiro, pelo `callIndex`, chama o virtualizer para posicionar e montar o Call e, em seguida, no quadro seguinte, após o reveal da busca expandir a mensagem e remedir, posiciona o Range de texto específico. Os pedidos de posicionamento usam uma match key estável para deduplicar, evitando rolamentos repetidos por ResizeObserver ou remontagem de linhas virtuais. Anterior/próximo dão a volta nas extremidades; uma trajetória truncada busca apenas nos registros já carregados e continua exibindo o aviso de truncamento existente.

- A trajetória faz virtualização de altura dinâmica por Call Card (uma chamada de modelo), sem dividir o INPUT / OUTPUT interno do cartão nem as linhas de mensagem. O contêiner de rolagem continua sendo o contêiner nativo `overflow-y-auto` já existente do painel.
- Os itens virtuais usam medição da altura real do DOM; após expand, recolher ou «mostrar tudo», qualquer mudança de altura precisa ser remedida; um pequeno overscan é mantido acima e abaixo para evitar flash branco em rolagens rápidas.
- A tela virtual externa continua oferecendo o grid de três colunas compartilhado. Linhas de medição de rótulo de papel com altura zero e invisíveis participam do cálculo da largura `max-content` da primeira coluna, garantindo que, quando a quantidade de itens virtuais montados varia, as colunas de conteúdo de SYSTEM / USER / ASSISTANT / TOOL não saltem horizontalmente.
- O estado de expansão de uma mensagem individual precisa ser mantido por uma chave de mensagem estável fora do Call Card; depois que o item virtual sai da viewport e é desmontado e depois remontado, o estado anterior à saída é restaurado. Os comandos de expansão em massa continuam sobrescrevendo o estado antigo de linha por meio da command version compartilhada, sem permitir que cada linha sincronize em um segundo momento por effect.

```text
native scroll viewport
        │ scrollTop / viewport height
        ▼
Call Card virtualizer ── overscan ──> visible Call Cards only
        │                              │
        │ dynamic measurement          └─ INPUT / OUTPUT / message rows
        └─ total canvas height

row toggle ──> keyed expansion state ──> survives Call Card unmount/remount
bulk toggle ─> command(version + 1) ────> supersedes older keyed state
```

## Multi-plataforma

- A leitura de disco é centralizada na camada de serviço: o desktop lê o `~/.zcode/cli` local e o controle remoto pelo celular lê, via RPC, o diretório de mesmo nome no host remoto.
- A entrada está disponível tanto no desktop quanto no Web do celular (não é oculta no mobile); sem registros, exibe-se uma mensagem de estado vazio.
