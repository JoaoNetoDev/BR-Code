# Dynamic Workflow: Apresentação (spec)

Status: implementado. Este documento descreve como um workflow é desenhado, antes e durante
uma execução: o payload de exibição que a ferramenta entrega à GUI, a linha do tempo
construída a partir dele, a sobreposição de execução ao vivo, e as superfícies que os
mostram. O analisador que produz os grafos é
`apps/zcode-cli/packages/dynamic-workflow/docs/analysis.md`; o motor que produz os eventos
de execução é `apps/zcode-cli/packages/dynamic-workflow/docs/execution-engine.md`; o fluxo de
lançamento em torno da janela de confirmação é `docs/dynamic-workflow/launch.md`; o cartão de
conclusão, as notificações e a transcrição do script são
`docs/dynamic-workflow/transcript-and-notifications.md`.

## O que o usuário vê

Um workflow é desenhado como **uma linha do tempo horizontal**: um trilho, com as fases do
script como **estações** sobre ele, os subagentes de cada fase como **pílulas** penduradas sob
sua estação, e as arestas de fluxo de controle que saltam ou retornam como **arcos** no ar
acima do trilho. Fases cujos subagentes rodam ao mesmo tempo ficam em **trilhos paralelos**
entre uma bifurcação e uma junção. A mesma linha do tempo aparece em três lugares, e os três
a construzem com uma única função pura,
`buildWorkflowTimeline(graph, run)` (`packages/ui/src/components/workflow-timeline/timeline-model.ts`):

| Superfície | O que desenha | Dados da execução |
|---|---|---|
| As linhas da ferramenta `CreateWorkflow` e `AmendWorkflow` no chat | enquanto o modelo ainda escreve: apenas a linha de fases, escrita por uma caneta; depois, um resumo de uma linha | nenhum |
| A janela de confirmação | a linha do tempo completa, estática, acima do script recolhido | nenhum |
| O cartão de execução sob o turno (`WorkflowRunDigest`) | a linha do tempo, ao vivo: lâmpadas, pílulas e tinta acompanham a execução | `workflowRuns` |
| O painel lateral da execução | o mesmo modelo lido verticalmente como uma **espinha**: uma seção por fase, pílulas como linhas, perguntas sob quem perguntou, artefatos no fim | `workflowRuns` |

A linha do tempo muda de forma durante uma execução de exatamente um jeito: em um
**preenchimento**, quando o agente principal escreve o corpo de um buraco e um novo payload de
exibição para o script efetivo substitui o antigo ("Buracos na linha do tempo"). Entre
preenchimentos o conjunto e a ordem de estações, trilhos e arcos é fixo; uma execução só muda
lâmpadas, status das pílulas e tinta, e só pode adicionar pílulas (quando um cartão se divide
em cartões por instância). Não há imagem do fim da execução: a última estação é a última fase,
e nada marca "pode terminar aqui".

O status nunca é só cor. Toda lâmpada fica ao lado de uma palavra ou de um ícone com
`aria-label`, e uma pílula `pending` é pixel a pixel idêntica a uma estática.

## O contrato de exibição

A GUI nunca vê os grafos do analisador. Uma camada de delimitação em `packages/core`,
`boundCausalityGraph(causality, flow, handoff)`
(`apps/zcode-cli/packages/core/src/tool/handlers/create-workflow-graph-bounds.ts`), dobra o
grafo de causalidade, o grafo de fluxo de controle e o grafo de hand-off em um único payload de
exibição, `causalityGraph` (o campo mantém seu nome histórico). O mesmo payload viaja no
`display` da requisição de confirmação e na saída de ferramenta que é persistida na linha da
ferramenta, de modo que a janela de confirmação, a linha da ferramenta e o painel de execução
leem um único contrato. Três schemas o espelham campo a campo:
`apps/zcode-cli/packages/contracts/src/tools/create-workflow.ts`
(a autoridade), `packages/shared/src/zcode-protocol-v4/create-workflow-display.ts`, e o
protocolo v3; todos são `.strict()`.

```ts
interface CreateWorkflowCausalityGraph {
  steps: Step[];               // ≤ 64: sites de ask / world-read; a chave de junção do status da execução
  lanes: Lane[];               // ≤ 32: atores, mais `workspace` / `unknown`
  participants: Participant[]; // ≤ 64: um cartão por (fase, lane), em ordem de hand-off
  handoffs: Handoff[];         // ≤ 256: {from, to, back?, types?} entre participantes
  phases?: Phase[];            // ≤ 32: {id, name?, line?, column?, alongside?}, ordem de primeiro alcance
  phaseEdges?: Edge[];         // ≤ 128: {from, to, back?} entre fases
  phaseStreams?: Stream[];     // ≤ 128: {from, to} — a fase `from` alimenta a fase `to` enquanto ambas correm
  exits?: string[];            // fases após as quais o fluxo de controle pode completar normalmente
  sink?: string[];             // steps cujos artefatos chegam ao retorno
  holes?: Hole[];              // ≤ 32: {siteId, name, type, phase?, tail?}, os buracos abertos em ordem de código;
                               // uma fase ou step escrito por um preenchimento carrega `fill: <hole id>`;
                               // a fase própria de um buraco carrega o buraco que o contém
  truncated?: true;
}
interface Step { id; kind: "ask" | "world-read"; label; labelPattern?; line?; column?;
                 lane; lanes?; source?; phase?; repeat?: "stack" | "serial" }
interface Lane { id; name?; namePattern?: { head?; tail? }; line?; column? }
interface Participant { id; phase; lane; steps: string[]; member?: { index; of }; many?: true }
```

Os ids têm no máximo 64 caracteres; nomes e rótulos no máximo 128.

**Uma seta.** Uma aresta diz uma coisa, "roda depois", e carrega uma marca opcional: `back`
para a aresta de retorno de um laço. Os tipos de aresta do analisador, sua certeza e
exatidão, suas regiões e a região e certeza de um step nunca entram no payload; a GUI não
desenha nenhum deles. Arestas de fase são o quociente do fluxo de controle (ver analysis.md,
"O grafo de fluxo de controle"), então uma seta entre fases responde "para onde a execução
pode ir em seguida", não "qual fase precisa preceder qual". Hand-offs são o grafo de
causalidade quotientado por participante (analysis.md, "O grafo de hand-off"). Ambos são
reduzidos antes de serem enviados.

**Ordem de delimitação.** As coleções se referenciam entre si, então a camada as corta numa
ordem fixa e preserva a integridade referencial sobre a retenção: a UI nunca deve receber um
id que aponte para nada.

1. Steps: os primeiros 64 em ordem de código.
2. Lanes: apenas as lanes que sobreviveram a steps ficam de pé, em ordem do grafo, e então as
   primeiras 32. Um step cuja própria lane foi descartada vai embora; um step com conjunto
   possível apenas estreita.
3. Participants: os `steps` de um cartão estreitam para os que sobreviveram e um cartão que
   fica sem nenhum vai embora; então os primeiros 64 na ordem do analisador (o de abertura
   sobrevive, o da cauda não). Hand-offs que tocam um cartão descartado vão com ele, e então
   os primeiros 256; cada hand-off mantém no máximo 8 `types`. Os steps de um cartão
   descartado permanecem em `steps`, então o status da execução ainda faz junção por eles;
   eles simplesmente não têm cartão.
4. `sink`: os steps sobreviventes entre o `fedBy` do analisador.
5. Phases: a tabela de fases do grafo de fluxo de controle, inteira, incluindo fases apenas
   marcadoras (uma posição de controle pela qual se passa precisa aparecer). Arestas de fase:
   descartar qualquer aresta que toque `entry` ou `abort`; uma aresta para o `sink` do fluxo
   vira uma entrada em `exits`; descartar auto-laços; dobrar o resto por par ordenado, com
   `back` apenas quando toda aresta dobrada era um `loop`; então reduzir (abaixo). Se a tabela
   de fases exceder 32 ou a lista de arestas reduzidas exceder 128, o **vocabulário inteiro**
   é descartado: `phases`, `phaseEdges`, `exits` e todo `Step.phase` vão juntos, e `truncated`
   é definido. Metade de uma imagem de fases mentiria. Um participante cuja fase não está
   listada é realocado para `unphased`; seu id não muda.
6. Phase streams (abaixo): cortar em 128 depois das arestas de fase; mais de 128 descarta o
   vocabulário inteiro do mesmo jeito.

`phases`, `phaseEdges`, `phaseStreams`, `exits` e `Step.phase` são tudo-ou-nada: um script sem
marcador `phase()` não tem nenhum deles, e `exits` pode estar vazio dentro do grupo (um script
sem caminho de conclusão normal) mas nunca aparece fora dele. `phaseStreams` é omitido dentro
do grupo quando não há nenhum.

**Alongside.** Uma fase carrega `alongside`: as fases listadas cujos fios ainda estavam
rodando quando esta fase foi acessada (analysis.md, "Fios e quadros"), em ordem da tabela de
fases, no máximo 32 ids, omitido quando vazio. É um **fato de nó**, não uma aresta. O
controle não passou daquelas fases para esta; ambas estão simplesmente em voo. Então nunca
entra em `phaseEdges` e nunca passa pela redução, que a leria como "roda depois" e cortaria uma
aresta real em nome próprio. A camada de delimitação a copia da projeção de fluxo de controle
sob a mesma integridade referencial que as arestas recebem: uma referência a uma fase não
listada é descartada, o id próprio da fase é descartado, o resto é deduplicado em ordem e
cortado em 32. Ela viaja com o vocabulário tudo-ou-nada junto com `phases`, `phaseEdges` e
`exits`.

**Streams.** Um estágio escrito como um `future` que entrega itens ao próximo estágio através
de um canal (authoring.md, "Streams") é concorrente com ele, então a visão de fluxo de
controle relaciona os dois apenas por `alongside` e não tem seta entre eles: um pipeline de
cinco estágios chegou como cinco fios sem relação. A visão de **causalidade** sim vê o
hand-off: um `send` é uma escrita em um contêiner e o `for await` a lê de volta, então o
quociente de fases da causalidade carrega uma aresta `data` de produtor para consumidor. Um
**phase stream** `{from, to}` é uma aresta dessas cujas duas pontas estão lado a lado (o
`alongside` de uma lista a outra): dois fios vivos só podem trocar dados através de um
contêiner compartilhado, que é o que um stream é. Uma aresta `data` para uma fase que não
está ao lado — a escrita depois de `await Promise.all([...stages])` — já é asunto da seta de
controle e não é um stream, e dois futures sem canal entre eles não têm aresta `data` e
permanecem dois fios. A camada de delimitação lê `causality.phaseEdges` procurando o tipo
`data`, descarta auto-laços, arestas que tocam uma fase não listada e pares que não estão ao
lado, deduplica por par ordenado na ordem do analisador e corta em 128. Um stream não é um
`phaseEdge` e nunca passa pela redução (o quociente da causalidade chega já reduzido); uma
seta ainda significa apenas "roda depois". O analisador não vê um canal de realimentação (um
`send` posterior do consumidor no canal de um produtor vem depois da leitura do produtor na
ordem do walk), então todo stream que ele produz hoje aponta de um fio anterior para um
posterior; a UI desenha a direção que chegar.

**Redução sem tipo.** As arestas de fase dobradas são alimentadas ao `reduceOrdering` do
analisador, exportado exatamente para esse propósito: toda aresta para frente como um tipo,
toda aresta de retorno como um carregamento. Isso transforma a redução tipada em uma redução
sem tipo, que é o que um único estilo de seta precisa: o conjunto desenhado é um conjunto
gerador irredundante da relação "roda depois", com alcançabilidade inalterada, sem aresta
para frente implicada por um caminho de comprimento dois ou mais, sem aresta de retorno
implicada por frente → um salto de retorno → frente, e arestas de retorno nunca servindo
como testemunhas.

Ele reduz a **condensação**, não o próprio grafo
(`create-workflow-graph-fold.ts`). Pegue os componentes fortemente conexas das arestas para
frente dobradas — as arestas de retorno são excluídas, porque dizem "próxima rodada", e
contá-las encolheria um corpo de laço inteiro a um ponto e deixaria suas arestas genuinamente
redundantes indeletáveis. Uma aresta cujas duas pontas compartilham um componente sobrevive
incondicionalmente; apenas as arestas entre componentes são reduzidas, deduplicadas por par de
componente e tipo, e as sobreviventes são expandidas de volta sobre as arestas brutas. Uma
testemunha que passa por um nó que compartilha um ciclo com qualquer uma das pontas não
afirma nada sobre se o controle pode alcançar o alvo diretamente, então não pode apagar uma
aresta. Duas escolhas independentes que reutilizam o mesmo par de nomes de fases são o caso
que força a regra: o quociente carrega `left → right` e `right → left` como arestas de ramo
ordinárias, e reduzir o grafo bruto apaga `choose → left` na testemunha
`choose → right → left`, desenhando uma imagem que diz que o ramo sempre vai para a direita e
que `left` é um desvio a partir de `right`. Fases intercaladas (`a; b; a`) são um componente
pela mesma razão e mantêm suas arestas para frente nos dois sentidos. Hand-offs chegam já
reduzidos pelo analisador e aqui são apenas truncados.

**Texto.** Nomes, rótulos e afixos de padrão vêm de literais do script, então são cortados com
uma fatia segura para surrogates: um limite que cai depois de um surrogate alto descarta meio
caractere. Um nome de ator ou de fase vazio se torna um `name` ausente (a UI localiza o
fallback); um rótulo de ask vazio cai para o id do step; um padrão cujos afixos foram ambos
cortados é omitido em vez de enviado como `{}`.

**Payloads antigos.** O schema é estrito e não tem shim de compatibilidade. Uma exibição
persistida que carrega campos que o schema não conhece mais falha em `safeParse`, e a linha
da ferramenta cai para texto puro sem grafo. Esse fallback é agora o custo *inteiro* de um
campo desconhecido: desde 2026-09-21 o envelope v4 carrega todo payload de exibição como
`.optional().catch(undefined)`, então um payload que este lado não consegue ler é descartado
e o frame ainda é entregue (`docs/v4-refactor/10-protocol-spec.md` §4.4.5). Antes disso, uma
falha de exibição estrita rejeitava o frame inteiro e derrubava a subscription junto — duas
vezes, por uma chave adicionada cada vez. Duas exceções são tratadas, ambas pela mesma limpeza
pré-parse em
`apps/zcode-cli/packages/contracts/src/tools/tool-result-metadata.ts` que os dois pontos de
entrada de parse compartilham. Exibições persistidas enquanto existia o recurso withdrawal de
refinamento de nome carregam `refinedName` em lanes e fases e `refinedLabel` em steps, e essas
três chaves são removidas. Exibições `get_workflow_run` persistidas carregam `providerStop` em
seu `error`, escrito enquanto o cartão reutilizava o schema de erro da saída da ferramenta, e
essa chave também é removida.

**Quem lê o quê.** `phases` e `phaseEdges` viram estações, trilhos e arcos, `alongside` vira
faixas, e `phaseStreams` viram trilhos de stream e tiram fios de sua faixa. `participants`
viram pílulas, em ordem de payload. `steps` e `lanes` são a chave de junção e o material de
nomeação. `sink` decide se a fase implícita de um script sem marcadores conta como uma saída.
`handoffs` e `exits` são transportados e validados, mas nenhum componente os lê hoje
(ver "Questões em aberto").

## O modelo da linha do tempo

`buildWorkflowTimeline(graph, run)` é uma função pura, sem React, sem DOM e sem relógio. Sua
saída:

```ts
interface WorkflowTimelineModel {
  stations: TimelineStation[];   // uma por fase, na ordem declarada
  rails: TimelineRail[];         // duas estações lado a lado em um trilho
  arcs: TimelineArc[];           // toda outra aresta
  bands: TimelineBand[];         // fases paralelas, crescente por `from`; vazio sem `alongside`
  runningIndex?: number;         // a estação em execução (a mais à direita se houver várias)
  live: boolean;                 // uma execução participou
  draft?: { agents: number };    // só o modelo da caneta tem isto
}
interface TimelineStation { id; naming: { id; name? }; pills; status?; visited; rounds; onLoop; track; fraction?; typing? }
interface TimelineRail  { from; to; ink; kind?: "fork" | "merge" | "twin" | "stream" } // kind ausente = um trilho simples em um trilho
interface TimelineArc   { from; to; lane; ink; air; stream? }                 // `air` = em qual ar de qual trilho ele voa
interface TimelineTrack { stations: number[]; entry: TimelineInk; exit: TimelineInk }
interface TimelineBand  { from; to; pred?; join?; tracks: TimelineTrack[] }   // intervalo inclusivo; tracks[0] = a linha principal
interface TimelinePill { key; lane: LaneRef; laneClass; runtimeName?; avatarIndex?; status?;
                         instance?: { siteId; ordinal; sessionId? }; slot?: { siteId; ordinal };
                         workspace?: { phaseId }; stepIds; asking? }
type TimelineInk = "faint" | "strong" | "march";
```

**Custo.** O modelo é linear na execução: uma passada indexa os nós listados por
`(actorSiteId, actorOrdinal)` e cada cartão lê esse índice em vez de varrer `run.nodes`
novamente, então uma construção custa O(atores + nós) e nunca o produto deles — no limite
da tabela de 1024 atores e 1024 nós o produto é um milhão de comparações por frame. O modelo
também é construído **uma vez por par `(graph, run)`** e compartilhado por todas as superfícies:
o grafo e o estado da execução são objetos de protocolo imutáveis (uma execução alterada
chega como um objeto novo), então `buildWorkflowTimeline` memoiza pela identidade deles e a
segunda superfície de um frame — o cartão de execução e o painel de execução desenham a mesma
execução lado a lado — paga uma busca, não uma construção.

**A fase implícita.** Um script sem marcadores não tem vocabulário de fases. A UI lhe dá uma
fase, id `workflow` (localizado "Workflow"), antes de qualquer coisa: todo step e cartão é
realocado para ela, não há arestas de fase, e `exits` é `[workflow]` quando o script retorna
algo. `withImplicitPhase` devolve um grafo com o vocabulário inalterado (referencialmente igual,
de modo que a memoização se mantém). O `unphased` do próprio analisador (localizado
"Não agrupado") significa "antes do primeiro marcador" e é uma fase diferente.

**Estações** são as `phases` do payload na ordem declarada, que é a ordem dos primeiros
marcadores `phase()`. Não há ranqueamento: duas fases irmãs que compartilham apenas um
predecessor ficam na ordem declarada, e a aresta entre elas vira um arco — ou, quando as duas
são paralelas, nada, já que a bifurcação disse isso.

**Trilhos e arcos.** Cada aresta de fase cujas duas pontas estão listadas e são distintas é
dobrada uma vez por par ordenado e se torna um trilho ou um arco; a classificação está abaixo,
primeiro os trilhos e depois o que uma faixa faz às arestas que a tocam. Um arco é uma
**aresta de retorno** quando seu alvo está à esquerda de sua origem; a marca `back` do payload
não é consultada, porque o analisador classifica uma reentrada (um segundo marcador
`phase("plan")`) como aresta para frente e na linha do tempo ela ainda aponta para a
esquerda. Uma estação é `onLoop` quando é a origem ou o alvo de uma aresta de retorno, e
todo membro de uma faixa é `onLoop` quando um arco de retorno toca a faixa; somente tais
estações mostram uma contagem de rodadas.

**Faixas e trilhos.** `foldPhaseBands` (`timeline-bands.ts`) transforma `alongside` na imagem.
Ele trabalha apenas com índices de estação, sem ids, sem tinta e sem pixels, então o mini
trilho da barra lateral o compartilha (ver "A linha de execução da barra lateral"). A relação
é simetrizada primeiro: apenas a fase posterior pode relatar a anterior, e na tela as duas são
iguais. Componentes conexos com dois ou mais membros dão os intervalos `[min, max]`;
intervalos sobrepostos se fundem, e todo índice dentro de um intervalo é membro, com lacunas
fechadas por robustez (elas não ocorrem sem laços). Uma **faixa** é um tal intervalo. Seus
membros são divididos em **trilhos** por coloração gulosa de intervalos na ordem declarada:
cada membro pega o trilho mais baixo do qual nenhum membro é paralelo a ele, senão abre um
novo. O primeiro membro portanto sempre pega o trilho 0, a **linha principal**. Uma estação
fora de toda faixa tem `track: 0`.

**Streams tiram fios de dentro da faixa.** Com `phaseStreams` (ver "O contrato de exibição"),
dois membros são paralelos *para a coloração* apenas quando nenhum alcança o outro ao longo
de arestas de stream: um estágio e todo estágio a jusante dele são uma linha de trabalho,
por mais concorrente que seja sua execução, e pertencem a um trilho na ordem declarada. Uma
faixa cujos membros caem todos em um trilho é **dissolvida**: não é uma faixa, suas estações
ficam na linha principal sem bifurcação, sem junção e sem gêmeos, e são ligadas pelos trilhos
abaixo. Um pipeline de cinco estágios é portanto cinco estações em fila. Um fio que nenhum
stream alcança (um future lateral) ainda assim pega um trilho próprio, e a faixa continua
sendo uma faixa ao redor dele. `foldPhaseBands` recebe os streams como terceiro argumento
opcional; o mini trilho da barra lateral não passa nenhum, então suas faixas são as faixas de
`alongside` (ver "A linha de execução da barra lateral").

O `pred` de uma faixa é `from − 1` e seu `join` é `to + 1`, cada um apenas quando essa
estação fica fora de toda faixa e uma aresta sai dela para um membro, ou de um membro para
ela. Duas faixas lado a lado não têm nenhum dos dois; o que fica entre elas é um trilho
simples.

**Trilhos.** Um trilho liga duas estações que ficam lado a lado em um trilho. Existem cinco
tipos:

1. duas estações adjacentes fora de toda faixa com uma aresta entre elas, como antes; duas
   estações adjacentes sem aresta não têm trilho, e o trilho nunca mente;
2. dois membros consecutivos de um trilho, **incondicionalmente**: um trilho é um fio, e a
   aresta entre dois de seus membros pode ter sido reduzida — em uma cadeia de sobreposição
   `A → C` representa `A → B → C` com B no outro trilho, e o fio se quebraria de outro modo;
3. `pred` → o primeiro membro de cada trilho, simples para o trilho 0 e `fork` acima dele;
4. o último membro de cada trilho → `join`, simples para o trilho 0 e `merge` acima dele;
5. `twin`, entre dois membros declarados adjacentes de uma faixa que estão em trilhos
   diferentes. Apenas a saliência e a barra lateral leem um gêmeo; o cartão e a espinha nunca
   desenham um, e ele nunca marcha. Diz "estes dois são paralelos", não "o controle foi por
   aqui".
6. `stream`, para um phase stream entre duas estações que ficam lado a lado em um trilho:
   duas estações adjacentes fora de toda faixa (as de uma faixa dissolvida, tipicamente), ou
   dois membros consecutivos de um trilho. Ele substitui o trilho simples do mesmo par. Diz
   "alimenta, enquanto ambos correm", não "roda depois".

Um phase stream que não é adjacente em um trilho se torna um **arco** com `stream: true`: no
ar do trilho de ambos quando as duas pontas compartilham um trilho de faixa, senão no ar de
cima. Um stream entre dois trilhos de uma faixa não é desenhado; a bifurcação e a junção já
dizem que os dois correm juntos.

A `entry` de um trilho é a tinta de sua bifurcação, ou, sem `pred`, forte se e somente se seu
primeiro membro foi visitado; sua `exit` é a tinta de sua junção, ou, sem `join`, forte se e
somente se seu último membro foi visitado. A espinha tinta as ramificações de suas linhas de
bifurcação e junção a partir dessas duas.

**Arestas com faixas.** Uma faixa é um nó para uma aresta. Para uma aresta dobrada `(f, t)`,
com `B(x)` a faixa de `x`:

- **mesma faixa, mesmo trilho**: consecutivos no trilho → nada, o fio já diz isso; senão um
  arco no ar desse trilho.
- **mesma faixa, trilhos diferentes**: uma aresta para frente é descartada, porque a
  bifurcação já disse que o controle passou pelas duas; uma aresta de retorno se torna o
  auto-laço da faixa, um arco reenraizado para `from = B.to`, `to = B.from`.
- **uma ponta em uma faixa**: absorvida como o `pred` ou o `join` quando a ponta externa é
  adjacente à faixa; senão um arco reenraizado para a última estação da faixa quando sai e
  para a primeira quando chega, no ar de cima.
- **duas faixas**: um arco da última estação da primeira faixa para a primeira estação da
  segunda, ou um trilho simples entre elas quando as duas faixas ficam lado a lado.
- **ambas fora**: um trilho quando adjacentes, senão um arco, como antes.

Os arcos são deduplicados por ar e par de pontas após o reenraizamento. O **ar** de um arco é
o trilho em cujo ar ele voa: um arco dentro de um trilho permanece no ar desse trilho, tudo o
mais vai para o de cima, `R − 1` para `R` a maior contagem de trilhos de qualquer faixa e no
mínimo 1. Sem faixas não há o que dobrar, toda estação tem `track: 0`, todo arco `air: 0`, e os
trilhos são os que a regra antiga produzia, trilho por trilho.

**Lanes de arco.** Arcos recebem alturas por coloração gulosa de intervalos (`assignArcLanes`):
ordenados por extensão, o mais curto primeiro (a ordem do payload desempata), cada arco pega
a lane mais baixa na qual nenhum arco já colocado o intersecta em índice de estação, a
interseção contada em intervalos fechados (dois arcos que compartilham uma ponta de estação
fundiriam seus segmentos verticais). Arcos que não se tocam compartilham uma altura; arcos
aninhados empilham o de dentro baixo e o de fora alto; só arcos que se cruzam são empurrados
para cima. Lanes são atribuídas **por ar** (`assignAirLanes`): dois arcos que voam em ares
diferentes nunca se empurram, por mais que se cruzem em x. `arcLaneCount` é a lane mais alta
mais um,Asked por ar, e define quanto ar o renderizador deixa acima da linha daquele trilho.
As lanes mantêm dois arcos que compartilham uma estação separados em altura; os slots
terminais (ver "Trilhos e arcos" em "Desenhando a linha do tempo") mantêm seus verticais
separados em x.

**Pílulas.** As pílulas de uma estação são os participantes daquela fase da visão de
participantes ao vivo (ver "Dividindo cartões por instância"), em ordem de payload, que é a
ordem de hand-off com o de abertura primeiro. A lane do agente principal (`main`) nunca faz
uma pílula: seus únicos steps são buracos abertos, e um buraco aberto é desenhado como sua
própria estação (ver "Buracos na linha do tempo"), não como um subagente da fase que contém a
chamada `hole()`. O nome de uma pílula é o nome de runtime que o motor reportou para sua
instância vinculada quando há um, senão o nome de exibição da lane (ver "Nomes").
`avatarIndex` é atribuído pela primeira aparição de `lane@ordinal` em toda a linha do tempo,
de modo que o mesmo subagente mantém seu rosto entre fases e os primeiros nove subagentes
nunca compartilham uma cor. Em uma execução ao vivo uma pílula de agente carrega `slot`, a
identidade que ela entrega quando clicada: o ordinal da instância quando há um, senão o
ordinal que ela vai receber, `member.index + 1` para um cartão membro e 1 para um cartão
único ou `many` (o motor numera ordinais por site em ordem). Uma pílula de workspace carrega
`workspace: { phaseId }`. Uma pílula está `asking` quando `run.pendingQuestions` nomeia sua
instância.

**Registros de entrada da execução.** Uma estação é casada com `run.phases[]` por **nome**:
casamento exato primeiro e, quando o nome de exibição tem exatamente 128 caracteres (o
limite), um casamento por prefixo no nome de runtime (`phaseNameMatches`, `phase-name.ts`).
A mesma regra decide se uma estação é `run.currentPhase`. Uma fase sem nome (`unphased`,
`workflow`) nunca casa.

**O que uma estação observa.** `observePhase` percorre `run.nodes` e mantém aqueles cujo site
id é um dos steps membros da estação (`step.source ?? step.id`, a mesma chave que a sobreposição
usa) e cuja fase de nascimento pertence a esta estação (ver "Estreitamento por fase"). Deles:
`visited` (qualquer node, ou um registro de entrada), `rounds` (o maior ordinal de node, ou o
`rounds` do registro de entrada, o que for maior), e `fraction` = assentados / observados,
ausente quando nada foi observado.

**Status da estação.** Um **estágio** — uma estação com qualquer parceira `alongside` ou
qualquer stream, e pelo menos um step membro — pega sua lâmpada de seus próprios nodes e dos
estágios que a alimentam, nunca de `currentPhase` nem de seu registro de entrada. Todo future
de estágio roda seu marcador no instante em que começa, então "entrada" e "atual" não dizem
nada sobre ele: na execução disparadora todos os cinco marcadores rodaram em 108ms, um estágio
ainda esperando seu canal lia `done`, e o último estágio (o `currentPhase`) pegou o estado
final da execução sem ter rodado um node. A regra de estágio:

1. nenhum node observado: `pending` enquanto a execução está `pending` ou `running`; depois
   que termina, `done` quando a execução foi `completed` e a estação foi acessada, senão
   `pending`;
2. senão o valor da dobra, exceto que um estágio `done` permanece `running` enquanto a
   execução está viva e um estágio que a alimenta (uma fonte de stream) está **aberto**. Um
   estágio está aberto enquanto a execução está viva e ele está `running` ou `pending` pela
   dobra (nenhum node conta como pending), ou um estágio que o alimenta está aberto — um ponto
   fixo, então um ciclo de realimentação termina.

Uma estação que não é estágio, ou um estágio sem steps membros (uma fase apenas marcadora),
mantém a regra sequencial. Os nodes membros falam primeiro, depois o fluxo de controle:

1. Se os steps membros dobram (ver "Dobrando status") para `running` ou `failed`, isso.
2. Senão, se a estação é `currentPhase` e a execução está `pending` ou `running`: `running`
   (o fluxo de controle está aqui entre o primeiro despacho e o próximo marcador).
3. Senão, se é `currentPhase` e a execução terminou: `done` para `completed`, `failed`
   caso contrário (a falha aconteceu nesta fase, tenha ou não nodes; uma execução parada
   desenha como um node que falhou).
4. Senão o valor da dobra, se houver.
5. Senão `done` se a estação foi acessada, `pending` caso contrário.

Sem uma execução, toda estação é `undefined`, toda pílula `undefined`, todo trilho e arco
`faint`, sem rodadas, sem frações.

**Tinta.** Um trilho é `strong` quando ambas as suas estações foram visitadas, senão `faint`.
Um arco de retorno é `strong` quando sua origem foi visitada e seu alvo tem `rounds ≥ 2`; um
arco para frente, quando ambas as pontas foram visitadas. Um trilho de stream ou um arco de
stream é `march` quando ambas as suas estações estão `running` (itens estão cruzando agora),
senão `strong` quando seu alvo foi visitado (algo cruzou), senão `faint`. Um arco de stream não
é um laço: ele nunca torna uma estação `onLoop`.

**March** é a tinta da aresta que o fluxo de controle tomou para uma estação em execução, e
é decidido uma vez por estação em execução em vez de uma vez por linha do tempo: dois
trilhos de uma faixa podem estar rodando ao mesmo tempo, e cada um quer sua própria entrada.
Para uma estação em execução `r`:

1. um arco de retorno de reentrada que aterrissa em `r`, ou em `B(r).from` quando `r` está
   numa faixa, com origem visitada e `rounds(r) ≥ 2`, marcha, e nada mais para `r` marcha;
2. senão todo trilho não-gêmeo para `r` de uma origem visitada marcha, então uma junção
   recebe seu pedaço de linha principal e toda junção, e o primeiro membro de um ramo
   recebe sua bifurcação;
3. senão um arco que aterrissa em `r` de uma origem visitada.

Trilhos de stream e arcos de stream não participam: sua tinta foi decidida acima e diz se
itens estão cruzando, não de que lado o controle veio.

`runningIndex` ainda é a estação em execução mais à direita; é o que a câmera segue, não o
que marcha. A projeção não tem timestamps, então essa é a resposta mais honesta disponível e
uma aproximação conhecida.

`pillActivity(graph, run, pill)` conta os steps de ask e de world-read de uma pílula e nomeia
o step que está rodando (senão o último assentado, senão o primeiro); o painel mostra as
contagens, não o rótulo.

## Juntando instâncias de runtime

O analisador nunca aprende com uma execução. O motor reporta instâncias `{siteId, ordinal}`, e
a GUI decora a imagem estática por site id (analysis.md, "Juntando instâncias de runtime").

### Status do node

`statusOfRunNode` mapeia a fase de ciclo de vida de um node para o `StepRunStatus` de quatro
valores:

| Fase do node | Status | Por quê |
|---|---|---|
| `executing`, `repairing`, `nudged` | `running` | há uma requisição ao modelo em andamento |
| `settled` com outcome `ok` (cache incluído) | `done` | |
| `settled` com outcome `failed` ou `cancelled` | `failed` | o diário os distingue; a imagem de quatro valores não |
| `queued`, `dispatched`, `waiting` | `pending` | nenhuma requisição chegou ao provedor ainda |

### Dobrando status

`aggregateRunStatuses` é a única dobra, aplicada a um multiconjunto de status de instância:

- um conjunto vazio dobra para `undefined`: **ausência não é um status**, e nenhuma dobra
  inventa um;
- qualquer `running` → `running`, deliberadamente à frente de `failed`: o que o leitor mais
  precisa saber é se algo ainda está se movendo;
- alguns assentados e alguns enfileirados → `running`: começou, não terminou;
- todos enfileirados → `pending`;
- todos assentados → `failed` se algum falhou, senão `done`.

As quatro regras são testes "qualquer", então dobrar por site e depois por participante dá o
mesmo resultado que dobrar as instâncias diretamente. `collapseStatuses(stepIds, table)`
coleta as entradas que existem e as dobra; um step sem entrada não participa.

### A sobreposição

`workflowRunOverlay(run, graph)` (`components/workflow-graph/run-status.ts`) devolve uma
tabela **parcial** `statuses: Partial<Record<stepId, StepRunStatus>>`: um step para o qual
nenhuma instância foi observada não tem entrada. "Nunca rodou" e "enfileirado" não podem
compartilhar um valor; quando compartilhavam, um ramo cujo outro braço nunca roda (um receptor
ternário, um `if` sem `else`, um `catch` ignorado, uma cópia de conjunto possível não
selecionada) arrastava sua estação inteira para `pending` depois de terminada.

Cada step se torna um alvo com chave em seu **site id**, `step.source ?? step.id`. Uma cópia de
conjunto possível (`ask#2~actor#1`) e uma cópia de fase (`ask#1~phase#3`) compartilham um site
com suas irmãs, então um node encontrado por site id é admitido a um alvo só se passa pelas
reivindicações desse alvo:

- **lane**: uma cópia com `source` admite apenas nodes cujo `actorSiteId` é igual à sua lane.
  Um node sem `actorSiteId` é admitido em todas as cópias do site (iluminação excessiva, nunca
  uma imagem escura). Um step sem `source` não faz reivindicação de lane: o cartão único
  desenhado para um receptor com mais de quatro candidatos pode rodar em qualquer um deles.
- **fase**: um step com `phase` admite apenas nodes cuja fase de nascimento pertence a essa
  fase, decidido pelo vinculador de fases abaixo.

Um node cujo site id não está no grafo é ignorado; a sobreposição nunca adiciona ou remove
nodes. `animatedEdges` é true quando algum step está rodando.

### Estreitamento por fase

O motor carimba cada node e cada ator com `phaseName`, o nome da fase vigente quando seu
ordinal foi criado (o instante em que `agent()` ou `.ask()` rodou, não o instante em que o
evento foi emitido). O nome é o vocabulário que o motor e o analisador compartilham.
`phasesOf(name, graph, runHasVocabulary)` (`instance-phases.ts`) diz a quais fases de exibição
um carimbo pertence:

| Carimbo | A execução tem algum carimbo | Pertence a |
|---|---|---|
| presente | — | as fases cujo nome de exibição casa (`phaseNameMatches`) |
| ausente | sim | a fase sem nome (`unphased` ou `workflow`): o analisador coloca steps pré-marcador ali também |
| ausente | não | todas as fases (um CLI mais antigo, uma execução mais antiga, um script sem marcadores) |

Sempre que a resposta seria vazia, ela é todas as fases: melhor um subagente mostrado duas
vezes do que um subagente rodando escondido. `phaseBinder(graph, run)` memoiza essas respostas
e, quando o próprio grafo ainda não tem fases, responde "pertence" para tudo. O vinculador é
compartilhado pela sobreposição, pela visão de participantes e pela observação de estações,
então os três nunca discordam. Sem ele, um auxiliar chamado de cinco fases que faz fan-out de
vinte subagentes acenderia as cinco estações quando o primeiro lote rodou.

### Dividindo cartões por instância

`liveParticipantView(graph, run)` (`participant-model.ts`) é o único lugar onde um cartão
encontra suas instâncias. As instâncias de um cartão são os atores em sua lane que deixaram um
node nos **sites deste cartão** com um carimbo na fase deste cartão, mais atores que ainda não
deixaram node algum nesses sites e cujo próprio carimbo de nascimento pertence a esta fase,
ordenados por ordinal. Em uma execução sem carimbos isso se reduz a "todo ator na lane", o
comportamento antigo.

| Cartão | Instâncias | Resultado |
|---|---|---|
| `many` (família de tamanho desconhecido) | 0 | o cartão permanece, status pela dobra de steps |
| `many` | ≥ 1 | um cartão por instância, id `${id}@${ordinal}`; hand-offs copiados para cada |
| único | 0 | o cartão permanece |
| único | 1 | o cartão **vincula** a instância: id inalterado, nome de runtime exibido, status pela dobra de steps |
| único | ≥ 2 | dividido como `many`: multiplicidade de runtime vence multiplicidade estática |
| membro `[i]` (fan-out literal) | — | vincula a i-ésima instância por ordinal; nenhuma ainda → `pending`; instâncias além de `of` não recebem cartão |

O status de um cartão vinculado ou dividido é dobrado apenas a partir dos nodes daquela
instância nos sites do cartão, e uma instância sem node ali ainda é `pending`. Um cartão de
workspace não tem instâncias e nunca se move. Uma execução que terminou é reproduzida a
partir do diário, então uma sessão reaberta ainda mostra nomes de runtime.

### Nomes

Site ids são identidade; nomes são apresentação, e nenhum nome é jamais um site id. O nome de
exibição de uma lane (`laneDisplayName`, `lane-name.ts`) é, em ordem: a palavra fixa para uma
lane sintética ("Script" para `workspace`, um rótulo "não resolvido" para `unknown`); o
literal do autor `agent("planner")` inalterado (localizá-lo reescreveria o autor); o padrão de
nome renderizado como `head…tail` para um nome interpolado; senão "Subagente anônimo",
numerado `… N` apenas quando duas ou mais lanes de agente anônimo coexistem, em ordem de lane,
lanes com padrão não contadas. O nome de exibição de uma fase é seu `name`, senão a palavra
localizada para `unphased` ou `workflow`. A localização acontece no momento da renderização,
nunca no modelo memoizado: o usuário pode trocar de idioma no meio da sessão. Uma pílula mostra
o nome de runtime acima de tudo isso.
