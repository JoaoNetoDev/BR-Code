# Matriz de Cobertura E2E de Background da Sessão de Conversa

Este documento registra o limite de enumeração E2E das background runtime tasks da área de sessão. Ele complementa o agrupamento `BG` da matriz principal e cobre apenas a cadeia principal do desktop já implementada e confirmada.

> **Nota sobre o estado de cobertura**: o spec histórico consolidado `conversation-session-background.test.ts` está atualmente em
> `manual-review/pending`, portanto o `covered by` de BG01–BG24 indica que o spec candidato já tem as asserções correspondentes,
> e não que eles façam parte do gate E2E padrão. O spec de background V4 no diretório padrão atual cobre apenas os cases que ele referência explicitamente dentro da sua própria linha.

## Resumo de Funcionalidades

| Campo | Valor |
| --- | --- |

## Decisões de Limite

| Limite | Decisão | Inclui | Exclui / poda | Fonte |
| --- | --- | --- | --- | --- |
| Modo de client | Apenas `desktop-continuous` | cadeia desktop normal renderer/host/agent | restauração de accepted command em `web-remote-replayable` | `docs/architecture/message-flow.md` |
| Fontes de task | Cobre as capacidades principais em comum | `local_agent`, `local_bash` | artifact/superfície de provider de Workflow, convergidos à parte depois | implementação de background atual |
| Portador de notificação | É preciso validar o request visível ao provider | `<task-notification>` entrando no roundtrip active-loop válido mais recente, ou acordando como task-notification command quando o runtime está idle; persistência sintética com `source=background_task` | bolha de usuário real visível na UI | testes de runtime command queue / visible content |
| Interação com goal | Validar defer + notificação e depois o verifier | não enviar o verifier enquanto o background está rodando; verifier só no turno da notificação | permutação completa de stop/cancel manual de active goal | `target.ts` |
| Fila terminal do goal | explicit pass representa | entrada direta do main idle; entrada do verifier em voo enfileirada; reavaliação da fila imediatamente após o target completar | fail-open/cancel, goal/compact tipado, replayable no celular em matriz separada | H08/G1-10 + relato do usuário sobre o rastro de runtime da sessão |
| Background aninhado | aceito como ciclo de vida de child apenas para cleanup | cleanup de terminal de background Bash dentro do child runtime, timeout, cleanup de cancelamento | reescrita do resultado de Bash aninhado no output do Agent pai; main/goal esperando Bash aninhado | design de fila local ao runtime e semântica de ciclo de vida por owner |
| Controle de parada | apenas parada de task já-background | stop da UI via `session/cancelBackgroundTask`, stop do `TaskStop` voltado ao model | Ctrl+B / foreground-to-background, TaskOutput, leitura manual de output artifact | `TaskStop` / dispatcher de stop de background do runtime |
| Ações de result-turn | retry comum pertence apenas ao turno de assistant mais recente disparado por usuário real | primeiro trava o assistant mais recente de toda a linha do tempo e depois valida a causa canônica `origin=realUser` do mesmo turno; o resultado de background pode ter fork julgado de forma independente pelo histórico estável | retry comum em round de resultado background/synthetic; pular o assistant background mais recente para recuperar retry de turno antigo | `latestAssistantRetryOnly` |

## Donos de Estado

| Estado / fato | Autoridade | Espelhos / caches | Evidência |
| --- | --- | --- | --- |
| estado terminal de background task | `RuntimeTaskRegistry` / execution adapter / subagent runner | card de background task da projeção de UI, eventos de sessão | provider request, bloco de tool, logs de runtime |
| ordem das notification commands | runtime command queue | user notice sintético do session store | índice de request `/messages` capturado |
| histórico visível ao usuário | filtro shared de conteúdo visível + projeção de UI | lista de mensagens no DOM | `getMessages("user")` |
| verificação de active goal | target methods do agent runtime | resumo de target da UI | provider request contendo o prompt do verifier e o status do target |
| ações de row do assistant | `ProductProjection` da CLI | a UI só consome `row.actions` | rows de projeção live/cold + DOM do componente |

## Dimensões

| Dimensão | Valores / classes de equivalência | Inclui? | Motivo |
| --- | --- | --- | --- |
| fonte de background | Agent, Bash, Workflow | Agent/Bash sim; Workflow não | A superfície de artifact de provider do Workflow ainda não convergiu com a linha principal |
| active goal | nenhum, active | sim | o defer do goal verifier é o principal risco do background |
| momento da conclusão | antes do idle do turno pai, depois do idle do turno pai | sim, representativo | O Bash pode concluir muito rápido e cobrir o merge com o active-loop; o Agent usa replay delay para cobrir o idle wake de forma estável |
| runtime aninhado | apenas pai, child runtime | superfície do pai automatizada; child runtime apenas para cleanup | o background subagent conclui após o primeiro child turn complete e notifica a sessão pai; background Bash terminal posterior no child só faz cleanup do child runtime, sem reescrever o Agent output já concluído |
| entrega de client | desktop continuous, web replayable | apenas desktop | replayable é uma exigência separada de recuperação remota |
| status terminal | completed, failed/lost | completed é o caminho principal; 429 failed entra no E2E como caso único; outros failed/lost ficam nos core tests | o caso único de 429 prova a fidelidade de erro entre camadas para result, hover e restore; outras anomalias não são permutadas |
| mensagem do coordinator | SendMessage com child em execução em tool batch ou em model step apenas de texto, SendMessage após terminal do child | child em execução em tool batch E2E sim; text-only e resume de terminal core sim | tanto depois do tool batch quanto depois de um text-only normal a continuação do provider request do child usa coordinator input com role user; o resume de terminal continua coberto pelos core tests |
| fonte da parada | controle de UI, TaskStop do model, cleanup de runtime | controle de UI e TaskStop sim; cleanup de runtime em testes focados | cleanup é um fechamento interno de ciclo de vida e não precisa de E2E por caminho de usuário | testes do dispatcher de runtime |
| estado de loading do pai | foreground subagent child tool, background subagent child tool, foreground Bash tool | sim | a atualização de background child tool só atualiza os detalhes do card do Agent e não deve transformar a UI de pai idle em streaming; subagent em foreground e Bash comum em foreground mantêm a semântica original de streaming / ChatLoading | testes de task stream da UI + BG13/BG14 |
| colocação do child tool | mensagem do Agent pai antes de uma resposta principal posterior, resposta principal posterior existente antes do update do child | sim | a atribuição do update espelhado do child tool precisa ser decidida por `parentToolUseId` e não pode cair na mensagem de assistant mais recente | BG18 |
| gatilho de result-turn | entrada de usuário real, wake de background Agent, wake de background Bash | usuário real + um wake de background representativo em testes de projeção; Agent/Bash compartilham o invariant de origin | a elegibilidade de retry depende da causa canônica e não é permutada com o task kind | BG33 |
| momento da entrada de goal em background | main idle com child em execução, verifier em voo | sim | as duas janelas decidem startNow e enqueue/auto-drain respectivamente, e é exatamente o limite de corrida deste caso | BG34 |
| cardinalidade do drain de notificação em idle | primeiro request de notificação em voo, múltiplos pendentes no próximo drain, chegada após o claim | sim | o snapshot estrito next-available determina que um outer batch corresponde a um primeiro model request; itens que chegam após o claim ficam para o próximo drain válido, e durante a continuação de tool é permitido que o active-loop existente faça merge no próximo provider step do mesmo turno | BG36 + core tests focados |
| desfecho terminal do batch com claim | success, provider retry esgotado, stop/abort | apenas focado | o claim de command mantém at-most-once; o batch input persistido antes da query continua no transcript após failure/stop, e requests seguintes não podem perdê-lo nem injetá-lo de novo | core runtime/persistence tests |
| modo de admissão do Bash | background explícito, promoção por timeout elegível, hard timeout de `sleep` no primeiro token | sim | os três caminhos decidem se o deadline é limpo imediatamente, submetido para background no horário ou mata o processo | BG37-BG39 |
| momento do abort do pai no Bash | antes de spawn/commit, depois do commit | sim | o commit é a fronteira de passagem de ownership de foreground para background; só é permitido herdar o abort do pai antes do commit | BG38 + testes focados de corrida do adapter |
